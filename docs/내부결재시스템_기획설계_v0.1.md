## 1. 목적과 범위

### 1.1 목적
사내 결재 업무(출장·구매·휴가·일반 기안)를 X-Manager 안에서 전자결재로 처리한다.

- 종이 결재 폐지 → 이력 자동 보존, 분실 위험 0
- 모바일/원격에서도 결재 가능
- 구매 기안 → 거래처/부품 DB와 자동 연계, **승인된 구매는 PO 초안으로 즉시 생성**
- 휴가 잔여일수 자동 차감 (확장)

### 1.2 적용 범위
| 양식 | 우선순위 | 비고 |
|---|---|---|
| **출장 신청서** | MVP | 출장지/기간/목적/예상경비 |
| **구매 신청서** | MVP | 품목/수량/단가/거래처/사유 |
| **휴가 신청서** | MVP | 휴가 유형/기간/사유/대직자 |
| **일반 기안서** | MVP | 자유 양식, 제목+본문+첨부 |
| 비용 정산서 | Phase 2 | 출장/접대비 사후 정산 |
| 인사 관련 (입퇴사 등) | Phase 3 | HR 영역 확장 |

### 1.3 범위 밖
- 인사평가, 급여, 근태 관리
- 사외 결재(거래처 협력사 합의서 등)
- 결재 양식 빌더(드래그앤드롭) — 코드에서 양식 정의

## 2. 기능 요구사항

### 2.1 핵심 시나리오 (MVP)

#### 기안자 시나리오
1. 결재 메뉴 → "결재 작성" → 양식 선택 (출장/구매/휴가/일반)
2. 양식별 필드 입력 + 첨부파일 업로드
3. 결재라인 자동 추천 → 필요 시 수정
4. **임시저장** 또는 **상신(제출)**
5. 진행 상황 확인 (내 기안함)
6. 결재 완료 후 PDF 다운로드 가능

#### 결재자 시나리오
1. 알림 (in-app 배지) → 결재함 진입
2. 결재 대기 목록에서 항목 클릭 → 상세 보기
3. **승인 / 반려(사유 필수) / 보류**
4. 다음 결재자에게 자동 전달
5. 모든 결재 완료 시 기안자에게 알림

### 2.3 결재 워크플로우

```
[DRAFT]            ─ 기안자가 작성 중 (임시저장)
   │ 상신
   ▼
[SUBMITTED]        ─ 첫 결재자 대기
   │ 첫 결재자 승인
   ▼
[IN_REVIEW]        ─ 중간 단계 결재자들이 처리 중
   │ 마지막 결재자 승인
   ▼
[APPROVED]         ─ 최종 승인 완료

분기:
[REJECTED]         ─ 어느 단계든 반려 (사유 필수)
[WITHDRAWN]        ─ 기안자가 회수 (SUBMITTED 상태일 때만)
[ON_HOLD]          ─ 결재자가 보류 (사유 기록)
```

#### 결재라인 구성 방식
- **자동 추천**: 기안자 부서 → 부서장 → 임원 (직급 기반)
- **수동 편집**: 기안자가 라인 수정 가능 (결재자 추가/제거/순서 변경)
- **결재 단계 수**: 1~5단계 (보통 2~3단계)
- **건너뛰기**: 자기 자신이 결재 라인에 있으면 자동 패스

#### 결재 액션
| 액션 | 효과 | 사유 입력 |
|---|---|:---:|
| 승인 | 다음 결재자로 이동 또는 최종 승인 처리 | 선택 |
| 반려 | 상태 REJECTED, 기안자에게 반환 | **필수** |
| 보류 | 상태 ON_HOLD, 다른 결재자 처리 가능 | 권장 |
| 회수 (기안자만) | 상태 WITHDRAWN | 선택 |
| 위임 (확장) | 부재 시 다른 결재자로 이임 | 필수 |

### 2.4 권한 모델

| 역할 | 권한 |
|---|---|
| 일반 사용자 (USER) | 본인 양식 작성/제출/회수, 결재라인에 본인 포함된 건 결재, 본인 기안 이력 조회 |
| 부서장 | 위 + 부서 내 모든 양식 조회 (감독 권한) |
| 관리자 (ADMIN) | 전체 조회, 양식 강제 종결/삭제, 시스템 설정 |

기존 `users.role` (ADMIN/USER) + `users.position` + `users.department` 재활용.
신규 권한 컬럼은 추가하지 않는다.

### 3.2 테이블 명세

#### `approval_request` — 기안 본체
```sql
id                  SERIAL PRIMARY KEY
request_number      VARCHAR(20)  -- "AP-26-001" 형식
form_type           VARCHAR(20)  -- 'BUSINESS_TRIP' | 'PURCHASE' | 'LEAVE' | 'GENERAL'
title               VARCHAR(200) NOT NULL
status              VARCHAR(20)  -- DRAFT/SUBMITTED/IN_REVIEW/APPROVED/REJECTED/WITHDRAWN/ON_HOLD

requester_user_id   INTEGER FK users(id)
department          VARCHAR(50)  -- 기안 시점의 기안자 부서 스냅샷

-- 양식별 가변 필드는 JSONB로 (스키마 진화 유연)
form_data           JSONB

-- 검색/집계 편의를 위해 자주 쓰는 값은 컬럼으로도 노출
total_amount        NUMERIC(15,2)
currency            VARCHAR(10)
period_start        DATE
period_end          DATE

current_step_order  INTEGER      -- 지금 처리 중인 결재 단계
final_step_order    INTEGER      -- 총 결재 단계 수

submitted_at        TIMESTAMPTZ
approved_at         TIMESTAMPTZ
rejected_at         TIMESTAMPTZ
withdrawn_at        TIMESTAMPTZ

created_at          TIMESTAMPTZ DEFAULT now()
updated_at          TIMESTAMPTZ DEFAULT now()
```

#### `approval_line_step` — 결재 단계
```sql
id                  SERIAL PRIMARY KEY
request_id          INTEGER FK approval_request(id) ON DELETE CASCADE
step_order          INTEGER NOT NULL   -- 1, 2, 3...
approver_user_id    INTEGER FK users(id)
status              VARCHAR(20)        -- PENDING/APPROVED/REJECTED/SKIPPED/ON_HOLD
acted_at            TIMESTAMPTZ
comment             TEXT

UNIQUE(request_id, step_order)
```

#### `approval_action_log` — 액션 이력 (감사용)
```sql
id                  SERIAL PRIMARY KEY
request_id          INTEGER FK approval_request(id) ON DELETE CASCADE
actor_user_id       INTEGER FK users(id)
action              VARCHAR(20)  -- SUBMIT/APPROVE/REJECT/HOLD/WITHDRAW/COMMENT/EDIT
from_status         VARCHAR(20)
to_status           VARCHAR(20)
comment             TEXT
created_at          TIMESTAMPTZ DEFAULT now()
```

#### `approval_attachment` — 첨부파일
```sql
id                  SERIAL PRIMARY KEY
request_id          INTEGER FK approval_request(id) ON DELETE CASCADE
filename            VARCHAR(500)
filepath            VARCHAR(1000)
size                INTEGER
mimetype            VARCHAR(100)
uploaded_by         INTEGER FK users(id)
uploaded_at         TIMESTAMPTZ DEFAULT now()
```

## 4. API 설계

### 4.1 엔드포인트 개요
모두 prefix `/api/v1/approvals/`

| Method | Path | 설명 |
|---|---|---|
| POST | `/` | 신규 기안 생성 (DRAFT) |
| GET | `/` | 목록 조회 (필터: 상태/유형/내것/결재대기/완료) |
| GET | `/{id}` | 상세 조회 (단계/액션 이력 포함) |
| PUT | `/{id}` | 기안 수정 (DRAFT 상태에서만) |
| DELETE | `/{id}` | DRAFT 삭제 |
| POST | `/{id}/submit` | 상신 (DRAFT → SUBMITTED) |
| POST | `/{id}/withdraw` | 회수 (기안자, SUBMITTED일 때만) |
| POST | `/{id}/approve` | 승인 (현재 결재자) |
| POST | `/{id}/reject` | 반려 (사유 필수) |
| POST | `/{id}/hold` | 보류 |
| POST | `/{id}/comment` | 코멘트만 추가 (상태 변경 없음) |
| POST | `/{id}/attachments` | 첨부파일 업로드 |
| DELETE | `/{id}/attachments/{idx}` | 첨부파일 삭제 |
| GET | `/{id}/pdf` | 결재 완료문 PDF 다운로드 |
| GET | `/inbox/pending` | 내 결재 대기 |
| GET | `/inbox/processed` | 내가 결재한 이력 |
| GET | `/templates` | 양식 메타 (필드 정의 등) |
| GET | `/approval-line-suggest` | 부서/직급 기반 결재라인 추천 |

### 4.2 Permission 미들웨어
- 기존 X-Manager `get_current_user` Depends 재사용
- 각 endpoint에서 권한 체크 (기안자/결재자/관리자)
- 다른 사용자가 결재자 모드로 API 호출하면 403

## 5. UI / UX 설계

### 5.1 메뉴 구조
```
좌측 사이드바
├── 대시보드
├── 영업
├── 생산
├── 재고/부품
├── 거래처
└── 결재 [NEW]               ◀── 새 메뉴
    ├── 결재 작성
    ├── 결재 대기함  [3]    ◀── 미처리 건수 배지
    ├── 내 기안함
    └── 결재 완료함
```

### 5.2 주요 화면

#### A. 결재 작성 (양식 선택 → 작성)
1. **양식 선택 모달**: 4개 양식 카드 (아이콘 + 설명)
2. **작성 폼**: 양식별 동적 필드 + 공통(제목/첨부)
3. **결재라인 위젯**: 자동 추천 결과 표시 + 편집 버튼
4. **하단 버튼**: 임시저장 / 상신

#### B. 결재 대기함 / 내 기안함 / 완료함
- 통일된 리스트 UI (필터, 정렬, 검색)
- 카드뷰 또는 테이블뷰 토글
- 상태 색상 배지 (DRAFT=회색, SUBMITTED=파랑, APPROVED=초록, REJECTED=빨강)

#### C. 결재 상세 모달
- 상단: 기안자/제목/상태/번호
- 중단 좌측: 양식 내용 (가독성 위주 렌더링)
- 중단 우측: 결재라인 (단계별 결재자/상태/시각/코멘트)
- 하단: 첨부파일 / 댓글
- 액션 영역 (현재 결재자만): 승인 / 반려 / 보류 / 코멘트

#### D. 대시보드 위젯 (기존 대시보드 확장)
- "내 결재 대기 N건" / "내가 올린 진행중 N건"
- 최근 일주일 결재 처리 통계

### 5.3 알림
- **MVP**: in-app (사이드바 배지 + 토스트)
- **Phase 2**: 이메일 (기존 `users.email` 활용)
- **Phase 3**: Slack/Telegram 봇

### 5.4 모바일 친화
- 반응형 (기존 X-Manager 동일 기조)
- 결재 대기함은 모바일에서 카드뷰 기본
- 승인/반려는 큰 버튼

## 6. X-Manager 기존 모듈 연계

### 6.1 인증/사용자
- `users` 테이블 그대로 재활용
- `position` (사원/대리/과장/차장/부장/임원) — 결재라인 자동 구성 키
- `department` (SALES/PRODUCTION/MANAGEMENT) — 부서장 식별 키

### 6.2 거래처 연계 (구매 신청)
- `BusinessPartner` 검색 (기존 partner API 재활용)
- 새 거래처면 임시 free text + "거래처 등록" 링크

### 6.3 부품 연계 (구매 신청)
- `Part` 검색 (기존 part API 재활용)
- 신규 부품이면 free text + "부품 등록" 링크

### 6.4 PO 자동 생성 (구매 신청 → 승인 후)
- 구매 신청 승인 시 옵션 체크되어 있으면 `PurchaseOrder` DRAFT 생성
- 신청서 ↔ PO 양방향 참조 (감사 추적)

### 6.5 첨부파일 인프라
- 기존 `production_request` 첨부 패턴 재활용
- `storage/uploads/approval/` 폴더

### 6.6 PDF 출력
- 기존 WeasyPrint 인프라 재활용
- 결재 완료문 양식 (기안 내용 + 결재라인 + 도장/서명)

## 8. 의사결정 대기 항목 ⚠️

다음 항목들은 본격 구현 전에 확정이 필요합니다:

### 8.1 결재 단계 / 결재자 자동 추천 규칙
- **현재 가정**: 직속 상사(같은 부서 상위 직급) → 부서장 → (대표 또는 임원)
- 회사 조직도 / 직급 체계가 어떻게 되는지 확인 필요
- "사원 → 대리 → 과장 → 차장 → 부장" 식인지, "주임 → 대리 → 과장 → 부장" 식인지

### 8.2 양식별 결재 단계 수
- 휴가는 1~2단계, 구매는 금액 기준 단계 차등 (예: 100만원 이상은 3단계)?
- **금액 기준 차등** 도입 여부

### 8.3 구매 신청서 — 거래처/부품 강제 여부
- X-Manager에 등록된 거래처/부품만 선택 가능 vs free text 허용
- 추천: free text 허용 (소비재 등 부품 마스터에 없는 항목 고려)

### 8.4 휴가 — 잔여일수 관리
- MVP에서는 사용자가 "사용일수"만 입력 vs 시스템이 차감
- 추천: MVP는 입력만, Phase 3에서 자동 차감 (`users.annual_leave_balance` 필드 추가)

### 8.5 결재 회수 권한
- 기안자만 가능 vs 부서장도 강제 회수 가능
- 추천: 기안자만 가능, ADMIN은 강제 종결 가능

### 8.6 결재 완료문 PDF 양식
- 단순 텍스트 정리 vs 회사 직인/서명 포함 양식
- 추천: 견적서 PDF 인프라 재활용해 직인 포함 양식

### 8.7 검색/조회 범위
- 일반 사용자가 다른 부서 결재 건을 볼 수 있는가?
- 추천: 본인 관련(기안/결재) 건만 조회 가능, 부서장은 부서 내 전체, ADMIN은 전체

## 9. 리스크 / 주의사항

| 항목 | 영향 | 대응 |
|---|---|---|
| 사용자 부서/직급 누락 | 결재라인 자동 추천 실패 | 누락 시 수동 라인 작성 fallback |
| 결재자 부재 (휴가/퇴사) | 결재 정체 | 보류 + 위임 기능 (Phase 3), 관리자 강제 처리 |
| JSONB form_data 스키마 진화 | 양식 변경 시 기존 데이터 호환성 | 양식 버전 필드 추가 (`form_version`) |
| 첨부파일 용량 누적 | 디스크 압박 | 50MB 제한, 오래된 결재 첨부 아카이브 정책 |
| 동시 결재(같은 단계 여러 결재자) | 데이터 충돌 | MVP는 단일 결재자만, 병렬 결재는 Phase 3 |
