## 1. 🔴 Critical — 운영 통합 전 반드시 처리

### ① 업무 API 대부분이 완전 무인증
- **현상**: `app/api/v1` 약 20개 라우터 중 인증을 거는 파일은 `approval.py` / `project.py` / `auth.py` **3개뿐**. parts·bom·sales_document·inventory·purchase_order·business_partner·price·dashboard·code_master 등 **나머지 전부 인증 없이 호출 가능**.
- **영향**: 프론트(`src/api/client.ts:83`)가 토큰을 첨부하더라도 **백엔드가 검증하지 않으므로 보호는 클라이언트 측 장식**에 불과. 네트워크에 접근 가능한 누구나 전 업무 데이터 조회·변경 가능.
- **조치**: 최소한 전 라우터에 `require_auth` 선(先)부착. 세분화는 RBAC 강제적용 계획(`전자결재_RBAC_하이브리드_개발계획.md`) 0~1단계에서 처리.

### ② `/api/v1/admin/*` (DB 백업/복원/삭제)가 무인증
- **현상**: `app/api/v1/admin.py` 의 다음 엔드포인트에 인증 데코레이터 없음:
  - `POST /admin/restore` — **운영 DB 전체 덮어쓰기**
  - `POST /admin/sync`, `POST /admin/backup`, `DELETE /admin/backups/{filename}`, `GET /admin/system-info`
- **영향**: CORS `*`(⑤)와 결합 시 **인증 없는 임의 클라이언트가 운영 DB를 복원/삭제** 가능. 프론트 `requiresAdmin` 라우터 가드는 백엔드를 보호하지 못함.
- **조치**: 전 admin 엔드포인트에 `Depends(require_admin)` 부착.

### ③ JWT SECRET_KEY 하드코딩 — 게다가 `.env`가 무시되는 구조
- **현상**:
  - `app/core/auth.py:18` 이 자체 상수 `SECRET_KEY = "xbeamtech-xmanager-secret-key-2026"` 를 **하드코딩**하고 JWT 서명/검증에 사용(`auth.py:41,47,52`).
  - `app/core/config.py:48` 의 `settings.SECRET_KEY`(= `.env`에서 로드)는 **JWT 어디에서도 사용되지 않음**.
- **함정**: `.env.production`에 SECRET_KEY를 넣어도 **JWT에 전혀 반영되지 않음**. "환경변수로 옮겼다"는 보완을 해도 `auth.py`를 안 고치면 무의미.
- **영향**: 서명 키가 소스/리포에 노출 → **임의 사용자/관리자 토큰 위조** 가능.
- **조치**:
  1. `auth.py`가 `settings.SECRET_KEY`(환경변수)를 읽도록 수정.
  2. 기존 노출 키 폐기 후 **신규 난수 키**로 교체(현 `.env` 값들도 이미 노출 상태).
  3. 키 교체 시 기존 발급 토큰 전부 무효화됨(재로그인 필요) — 배포 공지.

## 2. 🟠 High — 운영 전 처리 권장

### ④ 전역 예외 핸들러가 traceback을 클라이언트로 반환
- `app/main.py:106-114` 가 모든 미처리 예외에 `{"detail": str(exc), "traceback": <전체 스택>}` 를 **응답 본문으로 전송**. 내부 경로·쿼리·구조 노출. 결재는 감사가 핵심이라 특히 부적절.
- **조치**: traceback은 서버 로그로만 남기고, 응답에는 일반 메시지(`{"detail": "Internal Server Error"}`)만.

### ⑤ CORS 전체 허용
- `app/main.py:32` `allow_origins=["*"]`, `config.py:53` 기본값도 `["*"]`.
- **조치**: 운영 도메인으로 출처 제한(`BACKEND_CORS_ORIGINS` 환경변수화).

### ⑥ 운영에서 DEBUG 로깅 고정
- `app/main.py:16` `logging.basicConfig(level=logging.DEBUG, stream=sys.stdout)` 하드코딩.
- **영향**: 운영에서 민감정보·SQL이 stdout으로 노출.
- **조치**: 환경별 로그레벨(운영 INFO/WARNING).

## 3. 🟡 Medium

### ⑦ 문서 채번 경합/오버플로
- `approval_service.py:93 _next_doc_number()` 가 `doc_number` **문자열 desc 정렬**로 max를 구함.
- 연 9999건 초과 시 `AP-2026-10000` 이 문자열 비교상 `...-9999` 보다 작아 채번이 깨지고, `IntegrityError` 재시도도 같은 잘못된 max를 반복 → 5회 후 실패.
- 현실적으로 연 1만 건 미만이면 안전하나 잠재 결함. **조치**: 시퀀스/숫자 파싱 기반 max 또는 DB 시퀀스 채번 검토.

### ⑧ 인가 부재로 전사 정보 과다 노출
- `/approvals/calendar`(전사 휴가/출장 + `leave_type`), `/approvals/approvers`(전 직원 명단), `/users/seal/{id}.svg`(타인 도장 미리보기)를 **로그인한 모든 사용자**가 조회 가능.
- 부서/직급 기반 접근제어 부재(RBAC 미도입)와 연결. **조치**: RBAC 도입 시 함께 범위 제한.

## 5. 참고 — 전자결재 모듈 자체는 견고함 (그대로 가져가도 됨)

운영 토대 문제와 별개로, 결재 핵심 로직 품질은 높음:

- **트랜잭션 경계 정확**: `ApprovalService` 가 의도적으로 `BaseService` 비상속, 다중 테이블 변경을 단일 `commit()` / 예외 시 `rollback()`.
- **동시성 제어**: 상태전이마다 `with_for_update()` 행 잠금 + `current_step` 재검증(`_get_locked`, `_guard_turn`).
- **감사 무결성**: actions/corrections에 UPDATE/DELETE 엔드포인트 부재. 관리자 정정도 화이트리스트 필드(`_CORRECTABLE_FIELDS`)만 + 원본 보존 + 정정이력 INSERT.
- **결재 API 인증 일관**: `approval.py` 전 엔드포인트 `require_auth`/`require_admin`, 문서 열람권한(`get_detail`)·차례 검증(`_guard_turn`, ADMIN 대결도 차단).
