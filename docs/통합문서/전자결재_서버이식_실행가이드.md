## 0. 한눈에 — 이식의 4가지 핵심 사실

1. **마이그레이션은 100% 추가형(additive).** 신규 테이블 17개 + `users`에 nullable 컬럼 추가 + 신규 테이블 1개 rename뿐. **기존 ERP 데이터(부품·거래처·영업·재고·사용자) 소실 위험 0**(전수검사·실데이터 드라이런 완료). 운영 head 가정 `h4i5j6k7l8m9` → 목표 `x7y8z9a0b1c2`(16개).
2. **신·구 코드가 같은 DB를 공존 가능** → 블루-그린 무중단 컷오버 성립(§14.2). 구 코드는 신규 객체를 참조 안 함.
3. **운영 API가 현재 인터넷에 무인증 노출 중**(라이브 확인). 배포 직후 **`RBAC_MODE=observe`** 로 로그인 강제부터 거는 것이 최우선.
4. **시크릿은 저장소에 없다.** `.env.production`/`.env.development`/`.env`는 `.gitignore`로 제외됨(DB비번·SECRET_KEY). 서버에서 직접 배치해야 함(§3.3).

## 1. 서버 컴퓨터의 Claude Code에게 먼저 줄 브리핑 (복붙용)

> 서버 PC에서 Claude Code를 열고 **아래 블록을 그대로 붙여넣어** 시작하라. 맥락·금지선·순서를 한 번에 준다.

```
너는 지금 운영 중인 X-Manager ERP 서버에서, 전자결재/연차/RBAC/구매집행이 통합된 새 버전을
이식하는 작업을 돕는다. 아래 사실과 제약을 먼저 숙지하고, 내 확인 없이 파괴적 작업을 하지 마라.

[저장소]
- 새 코드: https://github.com/CPsHyun/X-Manager.git (branch main). 이것을 가져와 배포한다.
- 시크릿(.env)은 저장소에 없다(.gitignore 제외). 서버의 실제 .env를 써야 한다.

[가장 중요한 사실]
- 이번 DB 마이그레이션은 전부 '추가형'이다(신규 테이블 + nullable 컬럼 + 신규테이블 rename).
  기존 운영 데이터(parts/partners/sales/inventory/users 등)는 삭제·변경되지 않는다.
- 운영 현재 alembic head는 h4i5j6k7l8m9로 가정한다. 목표 head는 x7y8z9a0b1c2(신규 16개).
  만약 실제 head가 다르면 거기서 멈추고 나에게 보고하라(정합성 점검 필요).
- 신·구 백엔드가 같은 DB를 공존할 수 있으므로 '블루-그린(대체 포트)' 무중단 배포가 가능하다.
- 이 서버의 업무 API는 현재 무인증으로 인터넷에 노출돼 있다. 배포 직후 RBAC_MODE=observe로
  로그인 강제를 거는 것이 보안상 최우선이다.

[반드시 지킬 순서] (상세는 저장소 밖 정본문서 기준, 아래 6단계)
1) 운영 DB를 pg_dump로 백업한다(무조건 선행).
2) 현재 운영 alembic head를 확인한다(`alembic current`). h4i5j6k7l8m9가 아니면 멈추고 보고.
3) 새 코드를 '새 디렉터리'에 clone한다(기존 운영 디렉터리는 건드리지 않는다).
4) 서버의 실제 .env.production을 새 디렉터리에 배치한다(아래 [.env] 참조). venv 생성 + requirements 설치.
5) `alembic upgrade head` 적용(추가형이라 빠름). 구 백엔드는 계속 떠 있어 서비스 유지.
6) 새 백엔드를 대체 포트(예: 8002)로 RBAC_MODE=disabled→스모크→observe로 재기동→스모크.
   문제없으면 리버스프록시 upstream을 새 포트로 전환(이때가 유일한 컷오버). 그 후 역할배정→enforce.

[.env (시크릿) 규칙]
- backend/.env.production 에는 최소: DATABASE_URL(운영DB), SECRET_KEY(32자+ 강한 난수, placeholder 금지),
  APP_ENV=production, RBAC_MODE(처음엔 observe 권장), BACKEND_CORS_ORIGINS(운영 접속 origin).
- SECRET_KEY가 약하거나 placeholder면 앱이 기동을 거부하도록 안전가드가 들어있다(정상 동작).
- SECRET_KEY를 새로 바꾸면 기존 발급 토큰이 전부 무효화돼 전원 재로그인이 필요하다. 사용자에게 공지.

[절대 하지 말 것]
- backend/scripts/seed_test_accounts.py 를 운영 DB에 실행 금지(더미계정 시드용, 운영 오염).
- DELETE/DROP/TRUNCATE를 운영 DB에 임의 실행 금지. 마이그레이션 downgrade 임의 실행 금지.
- 회사 원격(xbeamtech/xmanager)으로 push 금지. 이 작업은 CPsHyun/X-Manager 기준이다.
- RBAC_MODE=disabled 상태로 장시간 방치 금지(무인증 노출). 같은 작업창에서 observe까지 올린다.

먼저 위 1)~2)단계(백업 + 현재 head 확인)부터 수행하고, 결과를 나에게 보고한 뒤 다음으로 진행하라.
```

> 이 브리핑은 **시작 프롬프트**일 뿐, 실제 명령은 §14(블루-그린) 체크리스트를 따른다. 서버 Claude에게 정본문서 경로를 함께 알려주면(서버에 사본을 두거나 내용을 붙여넣어) 더 정확하다.

## 3. 서버가 새 코드를 가져오는 방법 (git)

> "서버에 푸쉬"의 실체 = **이미 GitHub(`CPsHyun/X-Manager`)에 올라간 코드를 서버에서 clone/pull** 하는 것. 코드는 GitHub를 경유한다(내 PC → GitHub은 완료됨, 다음은 GitHub → 서버).

### 3.1 (권장) 새 디렉터리로 fresh clone — 블루-그린과 정합
기존 운영 디렉터리를 건드리지 않고 새 위치에 받는다(롤백이 쉬움):

```bash
# 서버에서, 운영 코드와 별도 위치에
cd /opt/xmanager           # 예시 경로 (운영 배치 루트)
git clone https://github.com/CPsHyun/X-Manager.git xmanager-new
cd xmanager-new
git log --oneline -1       # f30de5b 확인
```

### 3.2 인증 (private 저장소)
`CPsHyun/X-Manager`가 private이면 서버도 인증이 필요하다. 서버 환경에 맞게 택1:
- **Personal Access Token(권장, 헤더리스 서버)**: GitHub → Settings → Developer settings → Tokens(classic, `repo` scope) 발급 → clone 시 username=`CPsHyun`, password=토큰. 또는 URL에 포함:
  `git clone https://CPsHyun:<TOKEN>@github.com/CPsHyun/X-Manager.git xmanager-new` (토큰이 셸 히스토리에 남으니 주의 — 가능하면 credential manager 사용)
- **GUI 서버**: 평소처럼 브라우저 로그인(Git Credential Manager) 팝업으로 인증.
- **배포키(Deploy key)**: 저장소 Settings → Deploy keys에 서버 SSH 공개키 등록 후 `git@github.com:CPsHyun/X-Manager.git` 로 clone(읽기전용 권장).

### 3.3 시크릿(.env) 배치 — git으로 안 옴
저장소엔 `backend/.env.example`(빈 템플릿)만 있다. 서버에서 실제 값 배치:
```bash
cp backend/.env.example backend/.env.production   # 또는 기존 운영 .env를 복사
```
`backend/.env.production` 필수 항목:
| 키 | 값 | 비고 |
|---|---|---|
| `DATABASE_URL` | 운영 PostgreSQL 접속 | **기존 운영 서버가 쓰던 그 값** |
| `SECRET_KEY` | 32자+ 강한 난수 | placeholder/짧으면 **기동 거부**(안전가드). 새로 바꾸면 전원 재로그인 |
| `APP_ENV` | `production` | 운영 로그레벨·가드 활성화 |
| `RBAC_MODE` | 처음 `observe` 권장 | 배포 직후 무인증 창 차단. 안정 후 `enforce` |
| `BACKEND_CORS_ORIGINS` | 운영 접속 origin | 실주소 확인 후(§13.2). 모르면 우선 `["*"]`+추후 제한 |

> 기존 운영 서버는 이미 자기 `.env`(실DB·키)를 갖고 있을 것이다. **그 파일을 새 디렉터리에 복사**하고, **새로 생긴 키(`RBAC_MODE`/`BACKEND_CORS_ORIGINS`/`APP_ENV`)만 추가**하면 가장 안전하다. 내 개발 PC의 `.env.production`(강난수 키 포함)을 그대로 쓰고 싶으면 git이 아니라 **안전한 수동 전송**(SCP 등)으로 옮긴다.

### 3.4 이후 평상시 업데이트 (2차 배포부터)
이미 clone된 서버 디렉터리는 다음 배포 때:
```bash
cd xmanager-new && git fetch origin && git pull origin main
# venv 의존성 변경 시: pip install -r backend/requirements.txt
# DB 변경 시: alembic upgrade head
```

## 4. 배포 실행 순서 (요약 — 상세는 정본 §14.2)

> **블루-그린(권장)**: 사용자 영향 ≈ 프록시 reload 1회. 상세 단계는 [수정사항.md §14.2](전자결재_시스템통합_수정사항.md).

1. **운영 DB 백업**(필수) — `pg_dump -Fc -f backup_YYYYMMDD.dump <DB>`
2. `alembic current` 로 현재 head 확인(`h4i5j6k7l8m9` 기대, 다르면 중단·점검)
3. 새 디렉터리 clone(§3.1) + `.env.production` 배치(§3.3) + venv `pip install -r requirements.txt` (+필요 시 GTK3)
4. `alembic upgrade head` (구 백엔드는 계속 서비스 중 → 무영향)
5. 프론트 빌드: `cd frontend && npm install && npm run build` → 새 정적 디렉터리에 배치
6. 새 백엔드를 **대체 포트(8002)** 로 기동(`RBAC_MODE=disabled`) → 8002 직접 스모크(로그인→기안→상신→승인→인쇄→파일다운로드)
7. 8002를 **`RBAC_MODE=observe`** 로 재기동 → 다시 스모크(인증 켠 상태 깨짐 없는지)
8. **프록시 upstream 8001→8002 전환(reload)** + 웹루트를 새 프론트로 → **유일한 컷오버**
9. **역할 배정**(영업팀=FULL / 비영업=APPROVAL_ONLY) + 신규모듈 초기설정(연차 입사일·일괄생성·`leave:manage`, 구매 집행담당) → 안정 후 **`enforce`**
10. 구 백엔드(8001)·구 프론트 디렉터리 **보관**(롤백용), 안정 확인 후 정리

> **신규 모듈 초기설정**(§13 체크리스트): ①연차 — 직원 입사일 입력 → "전 직원 일괄 생성/동기화"(공식 재계산, **`ensure_grants(force=True)` 1회 필수**) → 경영지원팀에 `leave:manage` 배정. ②구매집행 — 관리→전자결재→집행 담당 지정.

### 4.1 (권장 변형) staging DB로 먼저 검증 — 실서비스/실DB 무영향
운영 DB를 **복사한 별도 DB**로 새 코드를 먼저 돌려보고, 검증 끝난 뒤 진짜 운영 DB로 승격하는 방식. 실 사용자/실 데이터를 전혀 건드리지 않고 안심하고 본다.

```
[검증 — 실서비스 영향 0]
1) 운영 DB 백업(pg_dump)                         ← 안전망
2) 운영 DB 복사 → staging DB (pg_restore)
3) staging DB에 alembic upgrade head            (추가형이라 빠름)
4) 새 코드를 '대체 포트(8002)+staging DB'로 띄워 충분히 테스트  ← 실DB 안 건드림

[승격 — 검증 끝난 뒤]
5) (저트래픽) 진짜 운영 DB에 alembic upgrade head  ← 추가형이라 옛 서비스 계속 정상(공존)
6) 8002의 접속대상을 staging DB → '진짜 운영 DB'로 교체 후 재기동
7) 8002를 실DB로 스모크(disabled→observe)
8) 프록시 8001→8002 전환(컷오버) → 9) 옛 서비스 종료(보관)
```

> ⚠️ **절대 함정**: staging DB(복사본)로 **테스트하는 동안 직원들은 옛 서비스에서 실 DB에 새 데이터를 계속 쌓는다.** 그 **복사본 DB째로 승격하면 그 사이 데이터가 전부 유실**된다. → **테스트는 복사본(4), 실제 승격은 진짜 운영 DB(6 이후)** 로 반드시 분리.
> staging DB 생성이 권한상 번거로우면, 복사 없이 처음부터 **진짜 운영 DB를 공유**(추가형이라 신·구 공존 안전)해도 된다 — §4 기본 순서. 마이그레이션은 이미 실데이터 복사본에서 검증 통과.

## 5. 롤백 방법 (문제 발생 시) — 3계층

상황별로 가장 가벼운 것부터. **데이터는 추가형이라 대부분 코드/프로세스만 되돌리면 된다.**

### 5.1 권한 문제(로그인/403 폭주 등) — 가장 흔함, 코드 롤백 불필요
- `.env`의 **`RBAC_MODE=disabled`** 로 되돌려 백엔드 재기동. 권한 강제만 꺼지고 기능은 유지.
- 또는 모듈별 토글(관리→권한 적용)에서 문제 모듈만 off.
- 즉시 복구되며 데이터 영향 없음.

### 5.2 코드/앱 문제 — 블루-그린이면 즉시 복귀 (무중단)
> ⚠️ **중요 전제: 현재 서버에서 돌아가는 운영 코드는 git에 없다.** 그래서 롤백은 git이 아니라 **"옛 서비스를 그대로 살려둔 것"** 에 의존한다. 옛 코드 폴더·프로세스를 **건드리지/지우지 않는 것**이 곧 백업이다.
- **프록시 upstream을 다시 8001(구 백엔드)로 reload** + 웹루트를 구 프론트로. 구버전이 살아있으므로 **즉시 무중단 복귀** (git 불필요).
- 옛 프로세스를 이미 종료했으면: **옛 디렉터리에서 다시 기동**(안 지웠으면 그대로 있음).
- 옛 디렉터리가 손상됐으면: **배포 전에 떠둔 압축 스냅샷**(아래)을 풀어 복원 후 기동.

> 🛟 **옛 코드가 git에 없으므로, 배포 시작 전 '스냅샷 3종'을 안전한 위치(`~/rollback/`)에 반드시 떠둔다 — 이게 git을 대신하는 유일한 사본:**
> ```bash
> pg_dump -Fc -f ~/rollback/db_YYYYMMDD.dump <운영DB>                 # (A) 데이터
> tar czf ~/rollback/oldcode_YYYYMMDD.tar.gz -C <옛코드상위> <옛코드폴더>  # (B) 코드 (Windows면 폴더 zip)
> cp <옛코드>/backend/.env ~/rollback/old.env                         # (C) 옛 설정 + 실행포트/서비스명 메모
> ```
> (선택) 더 든든히: 서버에서 **지금 돌아가는 코드를 새 저장소에 `prod-baseline` 브랜치로 한 번 커밋**하면 진짜 git 롤백 지점이 생긴다. tar 스냅샷으로도 충분해 필수는 아님.

### 5.3 DB 문제 — 추가형이라 보통 불필요, 최후수단만
- 마이그레이션은 추가형이라 **구 코드는 새 테이블/컬럼을 무시**한다 → DB를 되돌리지 않아도 구버전 정상 동작. **5.2(코드 복귀)만으로 충분한 경우가 대부분.**
- 굳이 스키마를 되돌려야 하면(권장 안 함, 신규 결재 데이터 유실):
  ```bash
  alembic downgrade h4i5j6k7l8m9     # 운영 직전 head로. 신규 전자결재 데이터 삭제됨 — 신중
  ```
- 데이터가 손상된 최악의 경우에만 **백업 복원**(1번에서 받은 dump):
  ```bash
  pg_restore --clean --if-exists -d <DB> backup_YYYYMMDD.dump
  ```
  → 백업 시점 이후 운영 데이터도 사라지므로 **정말 최후수단**.

### 5.4 롤백 판단 빠른표
| 증상 | 1차 조치 |
|---|---|
| 로그인/권한 403 다발 | `RBAC_MODE=disabled` 재기동 (5.1) |
| 특정 모듈만 오류 | 권한 적용 탭에서 그 모듈 off (5.1) |
| 앱 전반 오류·크래시 | 프록시 upstream 8001로 복귀 (5.2) |
| 마이그레이션 도중 실패 | 중단 → 로그 확인 → 구 백엔드 유지(아직 컷오버 전) |
| DB 데이터 손상(드묾) | 백업 dump 복원 (5.3, 최후) |

> **핵심**: 블루-그린으로 배포하면 컷오버 전까지 구버전이 그대로 살아있어 **롤백 = 프록시 전환 한 번**이다. DB 백업은 0번 단계에서 **무조건** 받아둔다.
