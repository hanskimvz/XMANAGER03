## 1. 프로젝트 개요

### 1.1 목적

회사 내부의 기안, 휴가신청, 출장신청, 지출결의, 회의록 등 사내 문서를
종이/구두 결재 없이 X-Manager 안에서 작성 → 결재선 지정 → 승인/반려까지
처리하는 **전자결재 모듈**을 개발한다.

> 주의: 여기서 "결재"는 돈을 지불하는 결제(payment)가 아니라
> 문서 승인(approval) 워크플로를 의미한다.

### 1.2 왜 별도 솔루션이 아니라 X-Manager에 통합하는가

- 직원이 이미 X-Manager 계정으로 로그인해서 업무함 (이중 로그인 없음)
- 기존 부품/BOM 승인, 구매발주서 결재란(담당/팀장/이사/대표)과 자연스럽게 연결 가능
- 방산 업체 특성상 외부 SaaS보다 자체 서버 보관이 보안/감사 측면에서 유리
- 월 구독료 없음, 회사 규모(10~30명)에 과한 기능 없이 필요한 것만 구현

### 1.3 범위

| 구분 | 포함 | 제외 (당분간) |
|------|------|---------------|
| 결재 흐름 | 순차 결재 2~3단계, 승인/반려 | 병렬(동시) 결재, 합의 |
| 결재선 | 기안 시 기안자가 결재자 선택·변경 / 관리자 디폴트 설정 | 부서 기반 자동 라우팅 |
| 문서 | 자유 기안 + 표준 양식(휴가/출장/지출/회의록) | 외부 기관 제출용 공문 |
| 문서 출력 | 결재란+승인도장 포함 인쇄(HTML)·PDF | 외부 전자서명(공인인증) |
| 사용자 | 전 직원 (10~30명) | 외부 협력사 계정 |
| 관리자 | 디폴트 결재자 설정, 승인기록 사후 정정 | — |
| 알림 | 시스템 내 알림 → 이후 이메일 | 카카오톡/SMS |

### 1.4 예상 데이터 규모

- 사용자: 10~30명
- 결재 문서: 월 50~200건, 연 2,500건 이내 → PostgreSQL 단일 DB로 충분
- 첨부파일: 건당 평균 1~2개, 기존 files API/storage 재사용

## 2. 현재 시스템 분석 (최신 서버 코드 v0.32.0 기준)

> v0.2 검토 시점: 최신 운영 서버 코드(커밋 84bc927, v0.32.0)를 직접 분석해 반영함.
> R0.1 대비 PDF·에디터 스택과 사용자 모델이 바뀌었고, 전자결재에 그대로 쓸 수 있는
> 자산이 더 늘었다. 핵심은 **이미 깔려 있는 것을 다시 만들지 말 것.**

### 2.1 기술 스택 (전자결재도 동일 스택 사용)

| 구분 | 기술 | 전자결재에서의 활용 |
|------|------|---------------------|
| 백엔드 | FastAPI 0.110 + SQLAlchemy 2.0 + Pydantic 2 | `api/v1/approval.py` 라우터 추가 |
| DB | PostgreSQL 15 + Alembic | 결재 테이블 추가 (마이그레이션 v0.33.0) |
| 인증 | JWT (python-jose) + bcrypt, role(ADMIN/USER) | 기존 `require_auth`/`require_admin` 그대로 |
| 프론트 | Vue 3 + TS + Pinia + Tailwind | `ApprovalList/Write/DetailView.vue` 추가 |
| **본문 에디터** | **TipTap (@tiptap/vue-3) — 이미 설치됨** | 기안 본문 리치 에디터로 재사용 |
| 파일 | files API + storage 폴더 | 첨부파일 재사용 |
| **PDF 출력** | **WeasyPrint 65.1 (HTML→PDF) + Jinja2** | 결재 문서 PDF — HTML 템플릿 그대로 변환 |
| PDF(구) | reportlab (발주서 등 레거시) | 신규 결재 문서엔 미사용 |
| 배포 | Docker + Nginx (AWS) | 기존 배포 파이프라인 그대로 |

> **중요 변경**: v0.1에서 PDF를 reportlab으로 계획했으나, 최신 코드는
> 견적서/PI/CI를 **WeasyPrint로 HTML→PDF 변환**(`app/templates/pdf/*.html` + Jinja2)
> 하고 있다. 우리 출력 문서 예시가 이미 HTML이므로 **그 HTML을 Jinja2 템플릿으로
> 옮기면 인쇄·PDF가 한 벌의 템플릿으로 끝난다.** reportlab보다 결재란/도장 레이아웃
> 구현이 훨씬 쉽다.

### 2.2 그대로 재사용할 기존 자산 (재개발 금지)

- 3계층 구조: `api/v1/` → `services/` → `models/`, 의존성 주입(`deps.py`)
- 인증/권한: `require_auth`, `require_admin`, JWT 발급/검증 (`core/auth.py`)
- **PDF 생성 파이프라인**: `services/pdf/`(WeasyPrint, 한글 폰트 설정 `fonts.py`,
  harfbuzz 우회 패치) — 결재 문서 PDF도 이 모듈을 거쳐야 한글이 깨지지 않음
- **PDF 저장·감사 패턴**: `models/sales_document_pdf.py` + `services/pdf/storage.py`
  - 파일을 storage에 저장 + **SHA-256 해시** + 다운로드 횟수/시각 추적 + 버전별 보존
  - 저장소 추상화(`PdfStorage` 인터페이스, local→S3 교체 가능)
  - → 결재 문서 PDF 보관/감사에 이 패턴을 **그대로 복제**해서 쓴다
- 파일 첨부: `api/v1/files.py` + `storage/`

### 2.3 보완이 필요한 부분 (전자결재의 선행 조건)

최신 코드에서 `users.position`은 **이미 추가되어 있다**(마이그레이션 `w3x4y5z6a7b8`).
부족한 건 "기본 결재자"와 도장 정보뿐이다.

| 항목 | 현재 | 필요 |
|------|------|------|
| 역할 | ADMIN / USER 2종 | 그대로 유지 (결재 권한은 별도) |
| 부서 | department 문자열 (SALES/PRODUCTION/MANAGEMENT) | 그대로 활용 |
| 직급 | `position` 컬럼 **이미 있음** | 그대로 활용 (값 채우기만) |
| 영문이름 | `name_en` 컬럼 **이미 있음** | 영문 도장/문서에 활용 가능 |
| 디폴트 결재자 | 없음 | `approver_id` 컬럼 추가 |
| 도장 | 없음 | `seal_text` / `seal_image_path` 컬럼 추가 |

> 설계 원칙: 30명 이하 조직에서 완전한 조직도 테이블은 과하다.
> "내 디폴트 결재자 1명"을 사용자에 직접 저장하는 단순한 방식으로 시작하고,
> 조직이 커지면 그때 조직도 테이블로 확장한다.


## 4. 단계별 개발 로드맵

모듈 단위로 조금씩 확장한다. 각 Phase는 그 자체로 완결되어 실사용 가능해야 한다.

### Phase 1 — 핵심 결재 흐름 + 출력 (최우선)

목표: "자유 기안을 올리고, 2~3명이 순서대로 승인/반려하고, 완료 문서를 인쇄/PDF로 출력한다"

1. `users` 테이블 확장 (approver_id, seal 관련 — position은 이미 존재) + Alembic 마이그레이션
2. 결재 테이블 생성 (documents/lines/actions, + pdf 보관 테이블)
3. 기안 작성 API — 기안자가 **결재선(결재자) 직접 선택·변경**, 디폴트 결재자 자동 채움
   (본문 에디터는 **기존 TipTap** 컴포넌트 재사용)
4. 승인/반려 API (상태 머신 + 차례 검증) — 승인 시 **승인 도장 자동 생성**
5. 문서함 API (기안함 / 내 결재대기 / 완료함)
6. **문서 출력 API/화면** — 결재란+도장 Jinja2 템플릿 → 인쇄 HTML / **WeasyPrint PDF**
   (기존 `services/pdf/` 파이프라인 + `sales_document_pdf` 저장·해시 패턴 복제)
7. 관리자: **디폴트 결재자 설정** 화면
8. 프론트 화면 (목록 / 작성 / 상세·결재 / 출력)
9. 대시보드에 "결재 대기 N건" 배지

> 관리자 승인기록 사후 정정 기능(11장)은 Phase 1 또는 Phase 2 초에 추가.

### Phase 2 — 표준 양식 + 알림

1. 양식 시스템 (`approval_forms`): 휴가신청서, 출장신청서, 지출결의서, 회의록
2. 양식별 입력 필드는 JSONB로 저장 (양식 추가 시 코드 수정 최소화)
3. 결재선 템플릿 (예: "휴가는 항상 팀장 → COO")
4. 첨부파일 (기존 files API 연동)
5. 알림: 결재 차례 도래/반려/완료 시 시스템 내 알림, 이후 이메일(SMTP)

### Phase 3 — 운영 편의 기능

1. 대결(대리결재): 결재자 휴가 시 위임 설정
2. 참조(CC): 결재권은 없지만 열람 가능한 수신자
3. 회수/재상신: 기안자가 진행 중 문서 회수 후 수정 재상신
4. (출력 자체는 Phase 1에서 완성) 양식별 출력 레이아웃 정교화 — 도장/서명 이미지 포함
5. 검색/필터 (기간, 양식, 상태, 기안자)

### Phase 4 — 기존 업무와 연계 + 감사 강화

1. 부품/BOM 승인, 구매발주서 결재를 전자결재 엔진으로 일원화
2. 감사 로그 강화: 문서 해시(SHA-256) 저장으로 사후 변조 검증 (방산 감사 대비)
3. 통계: 부서별/양식별 결재 처리 시간, 월별 건수
4. (선택) 연차 잔여일 자동 차감 등 휴가 관리 연동

## 5. 데이터베이스 설계 (Phase 1 기준)

### 5.1 users 테이블 확장

```sql
-- position 은 v0.32 코드에 이미 존재 → 추가하지 않음
ALTER TABLE users ADD COLUMN approver_id INTEGER REFERENCES users(id);  -- 디폴트 결재자(관리자 설정)
ALTER TABLE users ADD COLUMN seal_text VARCHAR(10);     -- 도장에 새길 글자(보통 이름, 미설정 시 name에서 추출)
ALTER TABLE users ADD COLUMN seal_image_path VARCHAR(300);  -- 업로드한 도장/서명 이미지(선택). NULL이면 자동 생성 도장 사용
```

> `approver_id`는 **관리자가 설정하는 디폴트 결재자**다. 기안 시 자동으로
> 1차 결재자로 채워지지만, 기안자가 화면에서 자유롭게 변경·추가·삭제할 수 있다.

### 5.2 approval_documents (결재 문서)

```sql
CREATE TABLE approval_documents (
    id              SERIAL PRIMARY KEY,
    doc_number      VARCHAR(30) UNIQUE NOT NULL,   -- 문서번호: AP-2026-0001
    form_id         INTEGER REFERENCES approval_forms(id),  -- NULL = 자유 기안
    title           VARCHAR(200) NOT NULL,
    content         TEXT,                          -- 본문 HTML (TipTap 에디터 출력, Phase2: 양식 데이터는 form_data로 분리)
    form_data       JSONB,                         -- 양식별 입력값 (Phase 2)
    status          VARCHAR(20) NOT NULL DEFAULT 'DRAFT',
                    -- DRAFT(임시저장) / IN_PROGRESS(결재중) / APPROVED(승인완료)
                    -- / REJECTED(반려) / CANCELED(회수)
    current_step    INTEGER DEFAULT 0,             -- 현재 결재 차례 (1부터)
    drafter_id      INTEGER NOT NULL REFERENCES users(id),  -- 기안자
    drafted_at      TIMESTAMPTZ,                   -- 상신 시각
    completed_at    TIMESTAMPTZ,                   -- 최종 승인/반려 시각
    created_at      TIMESTAMPTZ DEFAULT now(),
    updated_at      TIMESTAMPTZ
);
```

### 5.3 approval_lines (결재선)

```sql
CREATE TABLE approval_lines (
    id              SERIAL PRIMARY KEY,
    document_id     INTEGER NOT NULL REFERENCES approval_documents(id) ON DELETE CASCADE,
    step_order      INTEGER NOT NULL,              -- 결재 순서 (1, 2, 3)
    approver_id     INTEGER NOT NULL REFERENCES users(id),
    status          VARCHAR(20) DEFAULT 'WAITING', -- WAITING/PENDING(내 차례)/APPROVED/REJECTED
    acted_at        TIMESTAMPTZ,                   -- 처리 시각
    comment         TEXT,                          -- 승인/반려 의견
    seal_snapshot   VARCHAR(300),                  -- 승인 시점 도장 이미지(자동생성 SVG 또는 업로드 경로) 스냅샷
    approver_name   VARCHAR(100),                  -- 승인 시점 결재자 이름(직급 변동 대비 스냅샷)
    approver_position VARCHAR(20),                 -- 승인 시점 직급 스냅샷
    UNIQUE (document_id, step_order)
);
```

### 5.4 approval_actions (감사 이력 — INSERT만 허용, 수정/삭제 금지)

```sql
CREATE TABLE approval_actions (
    id              SERIAL PRIMARY KEY,
    document_id     INTEGER NOT NULL REFERENCES approval_documents(id),
    actor_id        INTEGER NOT NULL REFERENCES users(id),
    action          VARCHAR(20) NOT NULL,  -- SUBMIT/APPROVE/REJECT/CANCEL/RESUBMIT
    comment         TEXT,
    acted_at        TIMESTAMPTZ DEFAULT now(),
    ip_address      VARCHAR(45)            -- 감사 추적용
);
```

## 6. 결재 워크플로 상태 머신

```
                  상신(SUBMIT)
   [DRAFT] ───────────────────▶ [IN_PROGRESS]
      ▲                            │  │  │
      │ 재상신(RESUBMIT)            │  │  └─ 기안자 회수 ──▶ [CANCELED]

   (수정 후)                        │  └─ 결재자 반려 ──▶ [REJECTED] ─┐
      └────────────────────────────│──────────────────────────────┘
                                   │
                       마지막 결재자 승인
                                   ▼
                              [APPROVED]  (최종 — 이후 변경 불가)
```

핵심 규칙 (approval_service.py에서 강제):

1. 승인/반려는 `current_step`의 결재자 본인만 가능 (차례 검증)
2. APPROVED 문서는 어떤 경로로도 수정 불가
3. 반려 시 즉시 종료 — 뒤 결재자에게 가지 않음
4. 회수는 첫 결재자가 처리하기 전(또는 진행 중 정책 선택)에만 가능
5. 모든 행위는 approval_actions에 기록 (삭제 API를 만들지 않음)

## 9. 승인 마크(전자 도장) 생성 방식

종이 결재의 "도장/사인"을 대체하는 부분이다. 외부 솔루션 없이 직접 구현한다.
세 가지 방식 중 **9.1(자동 생성 도장)을 기본**으로 하고, 원하는 사람은 9.2로 교체한다.

### 9.1 (기본) 시스템 자동 생성 도장 — 별도 준비물 없음

승인 버튼을 누르면 서버가 그 사람의 이름으로 **빨간 원형 전자 도장 이미지(SVG)** 를
즉석에서 생성한다. 직원이 도장 파일을 따로 만들 필요가 전혀 없다.

작동 원리(개념):

```
이름 "홍길동"  →  글자 수에 따라 배치
  - 2글자: 좌우 2칸
  - 3글자: 위1 / 아래2 (전통 인장 배치)
  - 4글자: 2x2
→ 빨간색(#C00) 원 테두리 + 가운데 이름 + 아래 작은 글씨로 날짜
→ SVG 문자열 생성 → 화면/PDF에 그대로 삽입
```

구현 메모(백엔드, 라이브러리 불필요):

```python
# services/seal_service.py (개념 코드)
def make_seal_svg(name: str, approved_date: str) -> str:
    chars = list(name[-3:])  # 성 포함 최대 3글자 사용 (긴 이름은 이름자 위주)
    # ... 글자 수별 좌표 계산 ...
    return f'''<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 100 100">
      <circle cx="50" cy="50" r="46" fill="none" stroke="#C00000" stroke-width="3"/>
      <!-- 이름 글자들 -->
      <text ...>{chars[0]}</text> ...
      <text x="50" y="88" font-size="9" fill="#C00000">{approved_date}</text>
    </svg>'''
```

- 장점: 직원이 아무 준비 안 해도 됨, 깨끗하게 인쇄됨, 위·변조 시 시스템 기록과 대조 가능
- 표시 정보: 이름 + 승인 일시(원 하단). 클릭 시 "결재자/일시/IP" 상세 표시

### 9.2 (선택) 직원이 도장/서명 이미지 업로드

실제 인감 이미지나 손글씨 서명을 쓰고 싶은 사람은 PNG(투명배경)를 업로드한다.
→ `users.seal_image_path`에 저장 → 승인 시 그 이미지를 도장 자리에 사용.

- 도장 만드는 법 안내: 무료 도장 생성 사이트에서 PNG 다운, 또는 흰 종이에 도장 찍어
  스캔/촬영 후 배경 제거(예: remove.bg). 권장 규격: 정사각형, 300x300px 이상, 투명 PNG.

### 9.3 위·변조 방지 (핵심)

도장 이미지 자체는 "표시"일 뿐이고, **진본성의 근거는 DB 기록**이다.

- 승인 순간 `approval_lines.seal_snapshot` + `approval_actions`(결재자 ID·일시·IP)에 기록
- 출력 문서 하단에 **문서번호 + 검증용 일련번호** 인쇄 → 위조 의심 시 시스템에서 원본 대조
- **본문 SHA-256 해시**: 기존 `sales_document_pdf`가 이미 PDF에 SHA-256을 쓰고 있어
  인프라가 갖춰져 있다. 결재 문서도 **Phase 1부터** 출력 PDF 해시를 저장 가능
  (별도 개발 부담 없음, v0.1 계획의 "Phase 4"에서 앞당김)

> 정리: "도장 그림은 누구나 흉내 낼 수 있지만, 시스템 결재 기록은 못 바꾼다"가 설계 철학.
> 단, 11장의 관리자 사후 정정은 **별도 수정 이력을 남기는 방식**으로만 허용한다.

## 10. 문서 출력 기능

### 10.1 출력 대상/형식

- 대상: 진행 중·완료 문서 모두 (완료 문서에는 모든 도장이 찍힘)
- 형식 1 — **인쇄용 HTML** (`/print`): 브라우저 인쇄 미리보기 → A4 인쇄. CSS `@media print` 적용
- 형식 2 — **PDF 다운로드** (`/pdf`): **WeasyPrint + Jinja2**로 서버 생성
  (기존 견적서/PI/CI와 동일 파이프라인 `services/pdf/` 재사용)

> 구현 전략: 인쇄용 HTML과 PDF가 **하나의 Jinja2 템플릿**(`templates/pdf/approval_ko.html`)을
> 공유한다. 화면 인쇄는 그 HTML을 그대로, PDF는 같은 HTML을 WeasyPrint로 변환.
> 한글 폰트는 반드시 `services/pdf`(fonts.py) 경유 — 직접 weasyprint import 금지.
>
> **도장 렌더링 주의**: 브라우저 인쇄본은 예시처럼 인라인 SVG를 쓰고,
> WeasyPrint PDF는 SVG 텍스트 호환 이슈를 피하기 위해 도장을 **CSS 원(border-radius)
> + 텍스트**로도 만들 수 있게 헬퍼를 둘 다 제공한다(둘 다 동일 모양).
>
> 생성된 PDF는 `sales_document_pdf`와 동일한 방식으로 storage 저장 +
> SHA-256 해시 + 다운로드 이력을 남긴다(별도 `approval_document_pdf` 테이블).

### 10.2 출력 문서 레이아웃 (표준)

```
┌───────────────────────────────────────────────┐
│ [회사로고]  엑스빔테크        ┌──┬──┬──┬──┐      │
│                              │담당│팀장│이사│대표│  ← 결재란
│                              ├──┼──┼──┼──┤      │
│                              │도장│도장│도장│   │  ← 자동 도장 + 일시
│                              └──┴──┴──┴──┘      │
│  문서번호: AP-2026-0001                         │
│  ───────────────────────────────────────       │
│  제 목 : 출장 신청의 건                          │
│  기안자 : 홍길동 (영업팀)   기안일: 2026-06-18   │
│  ───────────────────────────────────────       │
│  [본문 내용]                                     │
│  ...                                            │
│  ───────────────────────────────────────       │
```

## 11. 관리자 승인 기록 사후 정정

운영 중 승인 일시·내용에 명백한 오류가 있을 때 **관리자(ADMIN)** 가 정정할 수 있다.
단, 감사 무결성을 위해 **원본을 덮어쓰지 않고 수정 이력을 별도로 남긴다.**

### 11.1 동작 방식

1. 관리자가 `/admin/approvals/{id}/actions`에서 해당 결재 기록을 연다
2. 승인 일시, 의견, (필요 시) 본문 등 정정
3. 저장 시 시스템이 자동으로:
   - 원래 값 → 새 값, 수정한 관리자, 수정 사유, 수정 시각을 `approval_corrections`에 기록
   - 정정된 문서에는 "관리자 정정됨(YYYY-MM-DD)" 표식 표시

### 11.2 정정 이력 테이블 (신규)

```sql
CREATE TABLE approval_corrections (
    id              SERIAL PRIMARY KEY,
    document_id     INTEGER NOT NULL REFERENCES approval_documents(id),
    target_table    VARCHAR(40) NOT NULL,   -- 어느 테이블을 고쳤나 (actions/lines/documents)
    target_id       INTEGER NOT NULL,
    field_name      VARCHAR(40) NOT NULL,   -- 고친 필드 (acted_at, comment ...)
    old_value       TEXT,                   -- 원래 값
    new_value       TEXT,                   -- 새 값
    reason          TEXT NOT NULL,          -- 수정 사유 (필수 입력)
    corrected_by    INTEGER NOT NULL REFERENCES users(id),
    corrected_at    TIMESTAMPTZ DEFAULT now(),
    ip_address      VARCHAR(45)
);
```

### 11.3 안전장치

- 수정 사유 입력 필수, 미입력 시 저장 불가
- `approval_corrections`는 INSERT 전용 (관리자도 삭제 불가)
- 관리자 본인이 결재자인 문서도 정정 가능하나, 모든 정정은 위 이력에 남아
  사후 감사에서 "언제 누가 무엇을 왜 고쳤는지" 추적 가능
- 출력 문서에 정정 여부 표식이 남으므로 은폐 불가

> 설계 의도: "실무 오류는 고칠 수 있게 하되, 고친 사실 자체는 절대 숨길 수 없게" 한다.

## 13. 보안/감사 고려사항 (방산 업체 대비)

1. **이력 불변성**: approval_actions는 INSERT 전용, UPDATE/DELETE API 없음
2. **승인 완료 문서 잠금**: APPROVED 상태에서 본문/결재선 수정 불가 (서비스 계층 + DB 제약)
3. **IP 기록**: 결재 행위마다 요청 IP 저장
4. **문서 해시** (Phase 4): 승인 완료 시 본문 SHA-256 해시 저장 → 사후 변조 검증
5. **백업**: 기존 PostgreSQL 백업 정책에 결재 테이블 포함 확인
6. 방위사업청/체계업체 품질 감사 시 "승인 기록 추적성" 증빙 자료로 활용 가능

## 16. Claude Code 멀티에이전트 개발·검증 전략

이 모듈은 **Claude Code가 여러 에이전트(서브에이전트)를 나눠 쓰며 "만드는 에이전트"와
"검증하는 에이전트"를 분리**하는 방식으로 개발한다. 핵심 원칙은 하나다:

> **만든 사람이 자기 코드를 검사하지 않는다.**
> 코드를 작성한 에이전트와, 그 코드를 검증하는 에이전트를 반드시 분리한다.
> 검증 에이전트는 작성 맥락 없이 "기획서 + 결과물"만 보고 독립적으로 판정한다.

엔지니어가 디테일을 직접 검토하기 어려운 상황을 보완하기 위한 구조다.
사람은 "게이트 통과 여부"와 "검증 리포트"만 확인하면 된다.

### 16.1 에이전트 역할 분담

| 에이전트 | 역할 | 산출물 |
|----------|------|--------|
| **PM 에이전트** (메인) | 작업을 쪼개고 순서·의존성 관리, 게이트 판정 취합 | 작업목록, 진행상황 |
| **설계 에이전트** | 기존 코드 패턴 조사 → 모델/스키마/API 시그니처 설계 | 설계 노트 |
| **백엔드 빌드 에이전트** | models → schemas → service → router 구현 | 백엔드 코드 |
| **프론트 빌드 에이전트** | Vue 화면(목록/작성/상세/출력) 구현 | 프론트 코드 |
| **검증 에이전트 A (테스트)** | pytest 작성·실행, 상태머신·권한 시나리오 검증 | 테스트 + 통과 리포트 |
| **검증 에이전트 B (감사/보안)** | 코드를 읽지 않고 "기획서 vs 결과물" 대조, 보안·감사 규칙 점검 | 검증 리포트 |

> Claude Code에서는 PM 에이전트가 `Task` 도구로 빌드/검증 서브에이전트를 띄운다.
> 서로 의존성이 없는 작업(예: 백엔드 빌드 ↔ 프론트 스캐폴딩)은 **병렬**로 돌린다.

### 16.2 작업 분해 + 검증 게이트 (Phase 1)

각 작업(WU)은 **빌드 → 독립 검증 → 게이트 통과**를 거쳐야 다음으로 넘어간다.

| WU | 작업 | 의존 | 검증 게이트 (통과 조건) |
|----|------|------|------------------------|
| WU0 | 설계 노트(모델/스키마/엔드포인트 시그니처) | — | 기획서 5·7장과 1:1 일치, 기존 명명규칙 준수 |
| WU1 | Alembic 마이그레이션 (approver_id/seal, 결재 테이블) | WU0 | `alembic upgrade head` 성공 + `downgrade` 성공, position 중복추가 없음 |
| WU2 | 모델 + 스키마 | WU1 | import 에러 없음, 필드/제약이 5장과 일치 |
| WU3 | approval_service (상태머신) | WU2 | **상태머신 불변식 테스트 전부 통과**(16.3) |
| WU4 | 라우터 api/v1/approval.py | WU3 | OpenAPI 생성됨, 7장 엔드포인트·권한과 일치 |
| WU5 | 출력 템플릿 + WeasyPrint 연동 | WU3 | PDF 생성 성공, 한글 안 깨짐, SHA-256 저장됨 |
| WU6 | 프론트 화면 3종 + TipTap | WU4 | 타입체크(vue-tsc) 통과, 핵심 플로우 동작 |
| WU7 | 관리자: 디폴트결재자/사후정정 | WU4 | 정정 시 `approval_corrections` 자동 기록 확인 |

### 16.3 반드시 통과해야 하는 불변식(검증 에이전트가 강제)

상태머신·감사 규칙은 코드 리뷰가 아니라 **자동 테스트로 못박는다.**

1. 승인/반려는 `current_step` 차례의 결재자 **본인만** 가능 (타인 호출 시 403)
2. ADMIN이라도 **차례를 건너뛴 대리 승인 불가**
3. `APPROVED` 문서는 어떤 경로로도 본문·결재선 수정 불가
4. 반려 시 **즉시 종료**, 다음 결재자에게 넘어가지 않음
5. 회수는 **1차 결재자 처리 전에만** 가능, 이후엔 거부
6. `approval_actions`·`approval_corrections`에 **UPDATE/DELETE API가 존재하지 않음**
   (검증 에이전트가 라우터 전수 검색으로 확인)
7. 관리자 사후 정정 시 **수정 사유 없으면 저장 실패**, 정정은 항상 이력에 남음
8. 직접 `import weasyprint` 금지 — 반드시 `services/pdf` 경유 (한글 폰트)

### 16.4 검증 에이전트 운영 방식

- **독립성**: 검증 에이전트에는 빌드 과정 로그를 주지 않는다.
  "기획서(이 문서) + 변경된 파일 diff"만 주고 합격/불합격을 받는다.
- **이중화**: 테스트(에이전트 A)와 정적 점검(에이전트 B)을 분리해 한쪽이 놓친 것을
  다른 쪽이 잡게 한다.
- **게이트 실패 처리**: 불합격 시 PM 에이전트가 리포트를 빌드 에이전트에 돌려보내
  재작업 → 재검증. **사람에게는 통과/실패 요약과 리포트만 보고.**
- **고위험 항목**(권한·감사 불변식)은 별도 보안 리뷰 에이전트가 한 번 더 본다.

### 16.5 Claude Code 착수 프롬프트 (복붙용)

아래를 Claude Code에 그대로 주면 위 구조로 개발을 시작한다.

```text
H:\Electronic Approval System\전자결재시스템_개발기획서_v0.2.md 를 읽고
X-Manager(v0.32.0, FastAPI+Vue3+PostgreSQL)에 전자결재 모듈을 Phase 1 범위로 개발한다.

진행 방식:
1) 너(메인)는 PM 역할. 16.2의 WU0~WU7을 작업목록으로 만들고 의존성을 건다.
2) 각 WU는 빌드 서브에이전트가 구현하고, 끝나면 "기획서+diff만 받은"
   독립 검증 서브에이전트가 16.3 불변식과 16.2 게이트로 판정한다.
   빌드한 에이전트가 자기 코드를 검증하지 않는다.
3) 게이트 불합격이면 리포트를 빌드 에이전트에 돌려보내 재작업한다.
4) 의존성 없는 WU는 병렬로 진행한다.
5) 기존 코드 패턴(deps.py 주입, require_auth/require_admin, services/pdf,
   sales_document_pdf 저장·해시 패턴, 기존 alembic 명명규칙)을 반드시 재사용한다.
6) 사람에게는 각 게이트의 통과/실패 요약과 검증 리포트만 보고한다.

먼저 WU0 설계 노트를 만들고, 내가 확인하면 WU1부터 진행해줘.
```

> 권장: 위 프롬프트로 **WU0(설계 노트)까지만** 먼저 받고 사람이 한 번 확인한 뒤
> 실제 코드 생성을 진행하면, 방향 오류를 초기에 잡을 수 있다.
