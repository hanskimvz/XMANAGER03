# 전자결재 서버 이식 — 따라하기 (운영자용 단계별 가이드)

> 이 문서는 **서버 컴퓨터 앞에 앉은 당신**이 그대로 따라 하는 실행서다. 어려운 결정은 **서버의 Claude Code에게 위임**한다 — 각 단계에 **그대로 복사해 붙여넣을 명령**이 있다.
> 작성 2026-06-22. 짝 문서: [전자결재_서버이식_실행가이드.md](전자결재_서버이식_실행가이드.md)(원리·근거), [전자결재_시스템통합_수정사항.md](전자결재_시스템통합_수정사항.md)(정본).

---

## 🚦 시작 전에 — 3대 안전 원칙 (이것만 지키면 사고 안 남)

1. **기존에 돌아가는 운영 폴더·DB·프로세스는 절대 먼저 건드리지 않는다.** 새 코드는 **새 폴더 + 다른 포트 + (검증용) 복사 DB**로만 띄운다.
2. **무엇이든 시작 전에 백업.** DB 덤프 + 옛 코드 폴더 압축. (현 운영 코드는 git에 없으니 이 압축이 유일한 사본 = 롤백 카드)
3. **단계마다 멈춰서 확인.** Claude에게 "보고하고 멈춰"라고 시킨다. 결과 확인 후 다음으로.

> 💡 이 작업은 **저장소가 새로 만든 것**이고 **서버 운영 코드는 git에 없다**. 그래도 위 방식(옛 것을 살려둔 채 새 것을 옆에 띄움)이면 롤백이 된다. 옛 것을 안 지우는 게 핵심.

---

## STEP 0 — 준비물 확인 (시작 전 체크)

- [ ] 서버 컴퓨터 접근 (직접 또는 원격데스크톱/SSH)
- [ ] 서버에 **Claude Code** 설치돼 있음
- [ ] 본인 GitHub 계정(`CPsHyun`) 로그인 가능 (저장소가 private이면 필요)
- [ ] 서버에 `git`, `python`, `node`, `postgresql`(pg_dump 등)이 깔려 있음 (없으면 Claude가 알려줄 것)

> 모르는 항목이 있어도 괜찮다. STEP 3에서 Claude가 현재 서버 상태를 조사해 알려준다.

---

## STEP 1 — 서버에서 Claude Code 열고 '맥락' 주입

🧑 **당신이 할 일**: 서버 컴퓨터에서 터미널/Claude Code를 연다.

💬 **Claude에게 붙여넣기** (아래 블록 전체 복사):

```
너는 지금 운영 중인 X-Manager ERP 서버에서, 전자결재/연차/RBAC/구매집행이 통합된 새 버전을
이식하는 작업을 돕는다. 내 확인 없이 파괴적 작업(기존 폴더 삭제/덮어쓰기, DB DELETE·DROP, 기존
서비스 중단)을 하지 마라. 각 단계는 끝나면 결과를 보고하고 멈춰라.

[사실]
- 새 코드: https://github.com/CPsHyun/X-Manager.git (branch main). 이걸 새 폴더에 받아 배포한다.
- 시크릿(.env)은 저장소에 없다. 서버의 실제 .env를 써야 한다.
- 이번 DB 마이그레이션은 전부 '추가형'이라 기존 데이터(parts/partners/sales/inventory/users 등)는
  삭제·변경되지 않는다. 신·구 코드가 같은 DB를 공존할 수 있다.
- 현재 서버에서 돌아가는 운영 코드는 git에 없다. 그래서 롤백은 '옛 서비스를 그대로 살려두는 것'에
  의존한다. 기존 운영 폴더/프로세스를 절대 건드리지 마라.
- 배포 방식: 옛 서비스는 그대로 두고, 새 코드를 '다른 포트'로 띄워 검증한 뒤, 리버스프록시를
  새 포트로 전환(컷오버)한다. 문제 시 프록시를 옛 포트로 되돌리면 즉시 복귀.

먼저 "알겠다"고만 답하고, 내 다음 지시를 기다려라. 아직 아무 명령도 실행하지 마라.
```

✅ **확인**: Claude가 "알겠다" 하고 멈추면 OK.

## STEP 2 — 현재 운영 상태 '조사만' (아무것도 바꾸지 않음)

> 서버가 어떻게 구성됐는지(폴더·포트·DB·프록시·실행방식)를 먼저 알아야 한다. **읽기만** 시킨다.

💬 **Claude에게 붙여넣기**:

```
지금부터 '조사만' 해라. 아무것도 변경/설치/재시작 하지 마라. 아래를 찾아서 표로 보고하고 멈춰라.
1) 현재 운영 X-Manager 코드가 있는 폴더 경로
2) 백엔드가 어떤 포트로 떠 있는지, 어떻게 실행됐는지(systemd 서비스명? pm2? 수동 uvicorn? IIS?)
3) 백엔드가 보는 DB 정보: backend/.env(또는 .env.production)의 DATABASE_URL에서 DB이름/호스트
   (비밀번호는 가리고 보고)
4) 리버스 프록시 종류와 설정 파일 위치(nginx? IIS? caddy?), 프론트(정적파일) 경로
5) 현재 alembic head: 운영 코드 backend 폴더에서 `alembic current` 결과
6) git/python/node/pg_dump 설치 여부와 버전
이 정보로 다음 단계 명령을 맞춤 구성할 거다. 변경은 절대 하지 마라.
```

✅ **확인**: Claude가 위 6개를 표로 보고하면, 그 내용을 잠깐 저장해둔다(다음 단계에서 경로/DB이름/포트를 채워 넣음). 특히 **5)의 head가 `h4i5j6k7l8m9`인지** 본다 — 다르면 Claude에게 "이거 예상과 다른데 왜 그런지 점검해줘"라고 하고 진행 멈춤.

## STEP 3 — 백업 + 옛 코드 스냅샷 (롤백 카드 만들기)

> 옛 코드가 git에 없으니, **이 백업이 유일한 복원 수단**이다. 가장 중요.

💬 **Claude에게 붙여넣기**:

```
배포 전에 롤백용 스냅샷 3종을 ~/rollback/ (또는 디스크 여유 있는 안전한 폴더)에 만들어라.
기존 운영은 계속 돌아가는 상태에서, 읽기/복사만 한다.
(A) 운영 DB를 pg_dump로 백업: pg_dump -Fc -f <안전경로>/db_백업.dump <운영DB이름>
(B) 현재 운영 코드 폴더를 통째로 압축(tar.gz 또는 zip)해서 같은 안전경로에 보관
(C) 운영 .env 파일 복사 + 현재 실행 포트/서비스명을 메모 파일로 저장
끝나면 세 파일의 경로와 크기를 보고하고 멈춰라.
```

✅ **확인**: 백업 파일 3개가 생겼고 크기가 0이 아니면 OK. **이게 있어야 다음으로 간다.**

---

## STEP 4 — 새 코드 내려받기 (새 폴더에 clone)

🧑 **당신이 할 일**: 저장소가 private이면, clone 중 GitHub 로그인 창이 뜰 수 있다. **본인 계정(`CPsHyun`)으로 로그인**한다. (헤드리스 서버면 Claude가 토큰 방식을 안내할 것 — 토큰은 GitHub → Settings → Developer settings → Personal access tokens에서 `repo` 권한으로 발급)

💬 **Claude에게 붙여넣기**:

```
새 코드를 '기존 운영 폴더와 별개의 새 위치'에 clone 해라. 기존 폴더는 건드리지 마라.
- git clone https://github.com/CPsHyun/X-Manager.git  <새폴더이름, 예: xmanager-new>
- clone 후 `git log --oneline -1` 로 최신 커밋 확인해서 보고
- private이라 인증이 필요하면, 이 서버 환경(GUI/헤드리스)에 맞는 가장 간단한 인증법을 알려줘라.
끝나면 새 폴더 경로와 커밋 해시를 보고하고 멈춰라.
```

✅ **확인**: 새 폴더가 생기고 `docs/통합문서/` 안에 문서들이 보이면 OK. (이 문서들도 같이 받아짐)

## STEP 5 — 시크릿(.env) 배치

> 저장소엔 빈 템플릿(`.env.example`)만 있다. **실제 값은 STEP 3에서 백업한 옛 .env를 재활용**하는 게 가장 안전.

💬 **Claude에게 붙여넣기**:

```
새 폴더의 backend/.env.production 을 만들어라.
- STEP 3에서 백업한 기존 운영 .env 값을 기본으로 복사(특히 DATABASE_URL은 운영 그대로).
- 거기에 아래 키를 추가/확인:
  APP_ENV=production
  RBAC_MODE=observe        (처음엔 observe — 로그인 강제만, 권한차단은 나중)
  BACKEND_CORS_ORIGINS     (직원이 실제 접속하는 주소를 모르면 일단 ["*"], 나중에 제한)
- SECRET_KEY가 32자 이상 강한 값인지 확인(약하거나 placeholder면 앱이 기동을 거부함).
  기존 운영 키를 그대로 쓰면 재로그인 불필요. 새로 바꾸면 전원 재로그인 필요.
끝나면 (비밀번호는 가리고) 어떤 키들이 설정됐는지 목록만 보고하고 멈춰라.
```

✅ **확인**: `DATABASE_URL`, `SECRET_KEY`, `APP_ENV`, `RBAC_MODE`, `BACKEND_CORS_ORIGINS`가 있으면 OK.

## STEP 6 — (검증) 복사 DB로 새 서비스 띄워 테스트

> 실 DB를 건드리지 않고, **운영 DB를 복사한 staging DB**로 새 코드를 먼저 돌려본다.

💬 **Claude에게 붙여넣기**:

```
실 운영 DB와 실 서비스는 건드리지 말고, 검증용으로만 진행해라.
1) 운영 DB를 복사한 staging DB를 만들어라(예: xmanager_staging). STEP3의 dump를 pg_restore.
   (DB 생성 권한이 없으면 멈추고 알려줘라 — 대안을 의논한다)
2) 새 폴더에서 백엔드 venv 만들고 requirements 설치, 프론트는 npm install + npm run build.
3) 새 backend/.env의 DATABASE_URL을 'staging DB'로 임시 변경.
4) `alembic upgrade head` 적용(목표 head: x7y8z9a0b1c2). 적용 결과 보고.
5) 새 백엔드를 '안 쓰는 포트(예: 8002)'로 띄우고, 그 포트로 직접 스모크 테스트:
   로그인 → 기안 작성 → 상신 → 승인 → 인쇄 → 파일 첨부/다운로드 → 영업/재고 핵심 조회.
끝나면 각 항목 성공/실패를 표로 보고하고 멈춰라. 기존 서비스(옛 포트)는 그대로 둔다.
```

✅ **확인**: 8002 포트에서 로그인·기안·승인·인쇄가 다 되면 검증 성공. **여기까지 실 사용자는 옛 버전 그대로 = 무영향.**

> ⚠️ staging DB 생성이 권한 때문에 안 되면, Claude와 의논해 **§4 기본방식(실 DB 공유)**으로 전환한다 — 추가형이라 안전하지만 "복사본 먼저"라는 안심은 줄어든다.

---

## STEP 7 — (승격) 진짜 운영 DB로 전환 + 컷오버

> 검증이 끝났을 때만. **테스트한 복사 DB가 아니라 '진짜 운영 DB'로 연결**해서 올린다(이걸 안 지키면 테스트 중 쌓인 데이터 유실).

🧑 **당신이 할 일**: 가능하면 **사용자가 적은 시간대**에 한다.

💬 **Claude에게 붙여넣기**:

```
검증이 끝났다. 이제 승격한다. 저트래픽 시간 가정.
1) 진짜 운영 DB에 alembic upgrade head 적용. (추가형이라 옛 서비스는 계속 정상 동작)
2) 새 backend/.env의 DATABASE_URL을 staging → '진짜 운영 DB'로 되돌리고 8002 재기동.
3) 8002를 진짜 운영 DB로 다시 스모크(로그인/기안/승인/조회). 이상 없으면 보고.
4) 리버스 프록시의 연결 대상을 옛 포트 → 8002로 전환(reload)하고, 프론트 정적 경로도 새 빌드로.
   이게 유일한 컷오버다. 전환 후 실제 접속이 새 버전으로 뜨는지 확인해서 보고.
각 단계마다 결과 보고하고, 4)번 컷오버 직전에 한 번 더 내 확인을 받아라.
```

✅ **확인**: 실제 접속 주소가 새 버전으로 뜨고 로그인/결재가 되면 컷오버 성공. **이제 무인증 노출도 닫힘(observe).**

---

## STEP 8 — 역할 배정 + 신규모듈 초기설정 → enforce

💬 **Claude에게 붙여넣기**:

```
컷오버가 안정적이다. 마무리 설정을 안내해라(관리자 화면에서 내가 직접 클릭할 부분은 클릭 순서로).
1) 권한: 영업팀 계정 = FULL 역할, 비영업 직원 = APPROVAL_ONLY 역할 배정(관리→권한 관리).
2) 연차: 직원 입사일 입력 → 연차 관리 화면 '전 직원 일괄 생성/동기화'(공식 재계산) →
   경영지원팀 역할에 leave:manage 배정.
3) 구매집행: 관리→전자결재→집행 담당 지정.
4) 위가 안정되면 RBAC_MODE=observe → enforce로 올려 8002 재기동(저트래픽 시간).
   문제 시 즉시 disabled로 되돌릴 수 있음을 기억.
각 단계 끝나면 보고하고 멈춰라.
```

✅ **확인**: 영업팀은 전부 그대로, 비영업은 전자결재만 보이면 정상.

---

## STEP 9 — 옛 서비스 정리 (단, 보관)

💬 **Claude에게 붙여넣기**:

```
새 버전이 하루 이상 안정적이면 옛 백엔드(옛 포트) 프로세스를 종료해라.
단, 옛 코드 폴더와 STEP3 백업은 '지우지 말고 보관'한다(롤백 대비). 종료 결과만 보고.
```

✅ **확인**: 옛 프로세스 종료, 옛 폴더·백업은 보관됨.

## 🔴 문제가 생기면 — 롤백 (어느 단계든)

증상별로 Claude에게 시킨다:

| 증상 | Claude에게 붙여넣기 |
|---|---|
| 로그인/권한 403 폭주 | `새 백엔드 .env의 RBAC_MODE=disabled로 바꿔 재기동해. 권한강제만 끄고 기능은 유지.` |
| 특정 모듈만 오류 | `관리→권한 적용에서 그 모듈만 enforce 끄는 법 알려줘.` |
| 새 버전 전반 오류(컷오버 후) | `프록시 연결을 옛 포트로 되돌리고 프론트도 옛 빌드로 되돌려. 옛 서비스는 살아있어야 한다. 즉시 복귀시켜.` |
| 옛 프로세스를 이미 껐다 | `옛 코드 폴더에서 옛 백엔드를 다시 기동해(STEP3 메모의 포트/명령 사용).` |
| 옛 폴더가 손상됨 | `STEP3에서 만든 옛 코드 압축본을 풀어 복원하고 기동해.` |
| DB 데이터 손상(드묾) | `STEP3의 DB 덤프로 복원해. 이건 최후수단이고 백업 시점 이후 데이터는 사라진다 — 진행 전 확인받아.` |

> 핵심: **컷오버(STEP7-4) 전까지는 옛 서비스가 그대로 살아있어 롤백 = 프록시 되돌리기 한 번.** 옛 폴더·백업을 안 지운 것이 안전망.

## 한 장 요약 흐름

```
STEP1 맥락주입 → STEP2 조사(읽기만) → STEP3 백업3종(롤백카드)
 → STEP4 새폴더 clone → STEP5 .env 배치
 → STEP6 복사DB로 검증(옛서비스 무영향) → STEP7 실DB 전환+컷오버
 → STEP8 역할/초기설정→enforce → STEP9 옛서비스 종료(보관)
문제? → 프록시 옛 포트로 되돌리기(즉시 복귀)
```
