## 1. 🔴 JWT SECRET_KEY 하드코딩 (가장 심각)

**위치:** `backend/app/core/auth.py:18`

```python
SECRET_KEY = "xbeamtech-xmanager-secret-key-2026"  # 운영 시 환경변수로 이동
```

**문제**
- 서명 키가 소스에 박혀 있어 git/zip으로 공개됨 → **누구나 임의 사용자·관리자 토큰 위조 가능**.
- `config.py:48`에 별도 `SECRET_KEY` 설정이 있으나 auth 모듈이 이를 **사용하지 않음**. `.env.production`에 키를 넣어도 무시됨.
- 결과: "결재자 본인만 승인", "관리자만 정정" 같은 권한 전제가 전부 무력화됨.

**수정 방향**
1. `auth.py`가 `from app.core.config import settings` 후 `settings.SECRET_KEY` / `settings.ALGORITHM` / `settings.ACCESS_TOKEN_EXPIRE_MINUTES`를 사용하도록 일원화.
2. 운영 키는 환경변수(`.env.production`)로만 주입.
3. 기동 시 키가 기본값(`your-secret-key-...` 또는 하드코딩 값)이면 **부팅 실패**시키는 가드 추가:
   ```python
   if settings.SECRET_KEY in ("your-secret-key-change-this-in-production", "xbeamtech-xmanager-secret-key-2026"):
       raise RuntimeError("운영 SECRET_KEY가 설정되지 않았습니다.")
   ```
4. 적용 후 기존 발급 토큰은 전부 무효화됨(재로그인 필요) — 정상 동작.

## 2. 🔴 전역 예외 핸들러가 스택트레이스를 클라이언트에 반환

**위치:** `backend/app/main.py:94-114`

```python
@app.exception_handler(Exception)
async def global_exception_handler(request, exc):
    error_detail = traceback.format_exc()
    return JSONResponse(status_code=500, content={"detail": str(exc), "traceback": error_detail})
```

**문제:** 모든 미처리 예외에 내부 경로·쿼리·스택을 응답 본문으로 노출. 공격자에게 시스템 구조 정보 제공.

**수정 방향**
- 운영 환경에서는 일반 메시지만 반환(`{"detail": "서버 오류가 발생했습니다."}`), traceback은 **서버 로그로만** 기록.
- 개발 환경(`APP_ENV=development`)에서만 상세 노출하도록 분기.
- `ResponseValidationError` 핸들러(`main.py:94`)도 동일하게 errors 노출 축소.

## 3. 🔴 환경설정 파일 / 자격증명 관리

**현황:** `backend/.env.production`, `.env.development`가 배포물(zip)에 포함됨 (실 DATABASE_URL·SECRET_KEY 포함).

**문제:** 실 자격증명이 외부로 유출되었을 가능성.

**수정 방향**
1. `.gitignore`에 `.env.production`, `.env.development` 명시적으로 추가 (현재 `.env`만 제외됨).
2. 배포·전달물에서 `.env.*` 제외, `.env.example`만 포함.
3. 실 자격증명이 노출된 적 있다면 **DB 비밀번호·SECRET_KEY 즉시 로테이션**.

## 4. 🟠 CORS 출처 전체 허용

**위치:** `backend/app/core/config.py:53`

```python
BACKEND_CORS_ORIGINS: list = ["*"]
```

**문제:** Bearer 토큰 방식이라 즉시 치명적이진 않으나, 운영에서 광범위.

**수정 방향:** 운영 환경은 사내망/실제 프론트 도메인으로 제한 (`.env.production`에서 주입). 개발은 `*` 유지 가능.

## 6. 🟡 감사 이력 DB 레벨 불변성 (Phase 4 감사 강화와 함께)

기획서 13장은 `approval_actions`/`approval_corrections`를 "INSERT 전용, UPDATE/DELETE API 없음"으로 규정하나, 이는 애플리케이션 약속일 뿐임.

**강화 방향 (방산 감사 수준):**
- DB 트리거로 해당 테이블 UPDATE/DELETE 거부, 또는 앱 DB 계정에 해당 권한 미부여.
- (Phase 4) 승인 완료 시 본문 SHA-256 해시 저장 → 사후 변조 탐지.
- 검증번호(`AP-2026-NNNN-XXXX`) 생성 규칙을 결정적으로 정의하고 대조 조회 화면 제공 (단순 랜덤이면 위변조 대조 기능 없음).
