# X-Manager 파일관리 통합 구현 계획서

**작성일**: 2026-07-30 (개정 2026-08)
**대상**: X-Manager v0.81+
**주제**: 이원화된 파일 관리(X-Manager ↔ Nextcloud) 통합 — "X-Manager = 파일 입구(Hub)"
**상태**: **Phase 1(1a·1b·1c) + Phase 2a 완료·배포** — 백엔드 API + 거래처/주문 파일함 + 경로 DB 저장 + 생성 PDF 자동 사본 + **레거시 '기존 폴더 연결'(수동 링크) UI**. 마이그레이션(`xm_v0810_nc_folder`) 적용 완료. **다음: Phase 3(선택 — 태깅/메타 검색·하위폴더 권한 세분화).** 상세 진행 이력은 문서 맨 아래 §17 참조.

---

## 1. 배경 및 문제 정의

업무 중 발생하는 파일이 많고, 일부(견적서·PI·CI 등)는 X-Manager로 이관됐으나 **제품 포장 사진, test report, 계약서, 데이터시트, 견적 산출자료** 등 대다수는 Nextcloud에서 관리 중이다.

문제는 **도구가 아니라 규칙의 부재**다:
1. "이 파일을 어디에 두는가"에 대한 단일 규칙이 없어 **같은 파일이 두 곳에 존재**하거나 **어디서 찾을지 몰라 헤맴**.
2. 클라우드 **폴더명을 사람이 손으로 지어** 제각각 → 뒤엉킴. (영업활동 폴더 생성 기능의 혼란도 기능 문제가 아니라 이 명명 문제에서 기인)
3. 결과적으로 직원들이 파일 위치·소재에 혼란을 겪음.

### 현황 (사실 확인 — 2026-08 실측)
- **클라우드**: Nextcloud. **회사 성격의 단일 계정**이 파일을 소유하고 공유(공유 폴더 모델 아님). 개인 종속 이슈는 없음(회사 계정으로 간주).
- **동기화 폴더**: `NEXTCLOUD_BASE_PATH = C:/Users/xbeam/Nextcloud/GBT`. **읽기·쓰기 가능 확인.** X-Manager 서버가 이 트리를 직접 다룰 수 있음(별도 API 불필요).
- **규모**: 실측 **44GB** (5년 누적).
- **as-is 구조(중요)**: 최상위(GBT) 아래 `수출/`, `국내판매/`, `견적/`, `계약서 …/`, `도면모음/`, `기타/` 등 + **낱개 파일 다수**(뒤엉킴). `수출/`·`국내판매/` 안은 **연도 우선**(`{연도}년 거래처별 수출/{국가}_{거래처}`)으로 5년치 존재. 또 거래처와 무관한 **채널/전사 공통 자료**(데이터시트 최신버전 모음, 가격리스트, 부대비용, 각종 양식·certificate 등)가 많음.
- **주 사용 부서**: 영업팀. 견적 산출자료·데이터시트·계약서 등이 거래처/주문/프로젝트 단위로 파생. 출하 단계에서 test report·포장사진 관리.
- **외부 공유**: 없음(전부 내부 전용).

## 2. 목표 / 비(非)목표

### 목표
- **혼란 제거**: "이 거래처/주문 파일 어디 있지?"를 없앤다.
- **X-Manager를 유일한 입구(Hub)**로 만들어, 파일 열람·업로드·기록을 X-Manager 안에서 수행.
- **결정적(자동) 폴더 체계**로 명명 불일치를 원천 차단.

### 비목표 (이번에 하지 않음)
- 파일시스템(Nextcloud) 폐기 ❌ — 저장소로 계속 사용.
- 모든 파일을 X-Manager DB/디스크로 이관 ❌ — 바이트는 Nextcloud에 둔다.
- Nextcloud 계정 구조 변경(공유폴더/그룹폴더 전환) ❌ — 현 단일 회사계정 유지.
- 외부(고객) 공유 기능 ❌ — 대상 파일 없음.
- Nextcloud 자체 권한 세분화 ❌ — 접근 통제는 X-Manager 입구에서.

## 3. 핵심 원칙

> **"기록은 X-Manager, 덩어리는 Nextcloud, 입구는 언제나 X-Manager."**

| 구분 | 저장 위치(바이트) | 접근 경로 | 예시 |
|---|---|---|---|
| 구조적 문서 | X-Manager가 생성/보관 | X-Manager | 견적·PI·CI·Invoice·PO, 생산요청/작업지시, 소량 첨부(도면·대표사진) |
| 대용량 작업 아티팩트 | **Nextcloud** | **X-Manager(입구) → 동기화 폴더** | 포장사진 다수, test report, 계약서, 데이터시트, 견적 산출자료 |

- X-Manager는 **저장소를 대체하지 않고 "내비게이터/입구" 역할**을 한다. 바이트가 어디 있든, 거래처/주문 화면의 **"파일" 한 곳**에서 접근.
- 원본을 X-Manager가 반드시 쥘 필요는 없음(사용자 확인). **열람·업로드·정리**가 X-Manager 안에서 되면 충분.

> **정확 매핑 원칙(핵심):** X-Manager는 폴더를 **추측(자동탐색)하지 않는다.** 자기가 만든 경로만 **DB에 기록해서 그것만 읽고 쓴다.** 사람이 손으로 만든 **레거시 폴더는 이름이 제각각이라 자동 매핑이 불가능** — 필요 시 **"기존 폴더 연결" 버튼으로 사람이 1회 수동 지정**만 허용한다. 이 원칙이 "신규는 정확, 레거시는 수동 링크" 전략의 근거다.

## 4. 확정된 결정 사항 (논의 결과)

| # | 항목 | 결정 |
|---|---|---|
| 1 | Nextcloud 계정 | **현행 단일 회사계정 유지** (이관/공유폴더 전환 안 함) |
| 2 | 저장 모델 | **Nextcloud=저장소, X-Manager=링크/입구** |
| 3 | X-Manager 원본화 필요 파일 | **없음** — 열람/기록만 되면 됨 |
| 4 | 업로드 주 경로 | **X-Manager를 통해 업로드** (Nextcloud 직접 진입은 "필요 시"만) |
| 5 | 접근 통제 | **X-Manager RBAC에서 팀별 통제** (생산직원은 영업탭 자체 미노출 → 파일도 차단) |
| 6 | 트리 최상위 축 | **거래처 우선** (연도는 거래처 하위) |
| 7 | 파일 탭 위치 | **거래처 상세 + 주문(PI) 상세** 양쪽 |

### 4-1. "거래처 우선"을 택한 이유
- 파일을 찾을 때 사람이 처음 떠올리는 축은 **거래처**이며 연도는 보조 조건.
- 연도 우선이면 한 거래처 자료가 연도마다 흩어져 "그동안 뭐 있었지?"를 한눈에 못 봄.
- 연도 무관 **상시자료**(카탈로그·데이터시트·계약서)의 자리가 명확(`거래처/_공통`).
- X-Manager 연동이 깔끔: "거래처 = 폴더 하나"로 대응 → 파일 탭이 한 곳을 가리킴.

### 4-2. 접근 통제 모델 (v1)
- 규칙 한 줄: **"그 거래처/주문을 X-Manager에서 볼 수 있는 사람 = 그 파일도 볼 수 있는 사람"** (기존 RBAC 상속, 별도 파일권한 미구축).
- **한계(수용됨)**: 통제는 X-Manager 입구에서만 작동. Nextcloud로 직접 들어가면 팀 제한이 없음(단일계정). 단, 생산팀 등은 영업탭 접근 자체가 막혀 실질 차단되며, 파일은 X-Manager 통해 보는 것이 전제.

## 5. 폴더 표준 트리 (거래처 우선 · X-Manager 전용 루트)

> **결정: 전용 루트로 분리.** 레거시 `수출/`·`국내판매/`(GBT 하위, 국내/해외 구분)는 **그대로 두고**, X-Manager가 관리하는 신규 트리는 **`국내업체/`·`해외업체/`** 두 갈래로 새로 만든다. 현행 업무 혼란을 피하고, 레거시 파일은 나중에 점진 이관.

```
GBT/
  수출/            ← 레거시(해외) — 그대로, 안 건드림
  국내판매/         ← 레거시(국내) — 그대로, 안 건드림
  해외업체/         ← ⭐ X-Manager 관리(신규)
     [국가]_[거래처]/
        _공통/                          ← 카탈로그·데이터시트·계약서·NDA (주문 무관 상시자료)
        [연도]/
           [주문(PI번호)·프로젝트]/
              01_견적·산출자료
              02_영업문서(PI·PO·CI)      ← X-Manager 생성 PDF 자동 사본
              03_도면·사양
              04_생산·검사(test report·성적서)
              05_포장·출하(포장사진·packing list·운송장)
              06_기타
  국내업체/         ← ⭐ X-Manager 관리(신규)
     [거래처]/
        _공통/ · [연도]/[주문]/01~06
```

- 거래처 우선: 한 거래처 = 폴더 하나(`해외업체/폴란드_CELLCO`, `국내업체/가나상사`).
- PI 발행 전 "프로젝트(딜)" 자료는 프로젝트 폴더에 쌓고, PI 발행 시 그 폴더가 주문 폴더가 됨.
- 고정 하위 폴더(01~06)는 주문/프로젝트 단위로 자동 생성.

### 5-1. 레거시와의 관계 ⚠️
- 레거시(`수출/`·`국내판매/`, 연도-우선)는 **손대지 않고 존치.**
- 신규는 전용 루트(`국내업체/`·`해외업체/`, 거래처-우선)에만 생성 → **레거시와 물리적으로 완전 분리**(혼선 없음).
- 레거시 파일은 나중에 전용 루트로 **점진 이관**(7·12장). 필요 시 "기존 폴더 연결"로 참조.

## 6. 명명 규칙 (결정적 자동생성)

**모든 폴더명은 시스템 값으로 자동 생성하며 사람이 손으로 짓지 않는다.**

| 레벨 | 규칙 | 예시 |
|---|---|---|
| 채널(전용 루트) | 국내업체 / 해외업체 (거래처 trade_type/국가로 판정) | `해외업체` |
| 거래처 루트 | `{국가한글}_{거래처명}` (해외) / `{거래처명}` (국내) | `폴란드_CELLCO` |
| 상시자료 | 고정 `_공통` | `_공통` |
| 연도 | `{YYYY}` | `2026` |
| 주문/프로젝트 | `{PI번호}` (PI 있음) / `{프로젝트명}` (PI 전) | `PI-CL250408` |
| 하위 | 고정 `01_…` ~ `06_…` | `04_생산·검사` |

- 파일/폴더명 금지문자는 기존 `sanitize()` 재사용.
- 거래처명 변경 시 폴더 리네임 이슈가 있으므로, **거래처 루트 경로를 엔티티에 저장**하는 방식을 권장(9-3 참조).

## 7. 아키텍처 / 연동 방식

```
[사용자 브라우저]
      │  (열람/업로드는 항상 X-Manager 통해)
      ▼
[X-Manager 프론트]  ──파일 탭──►  [X-Manager 백엔드 파일 브라우저 API]
                                          │ 읽기/쓰기 (경로 안전 + RBAC)
                                          ▼
                        [서버 로컬: NEXTCLOUD_BASE_PATH 동기화 폴더]
                                          │ Nextcloud 데스크톱 클라이언트 동기화
                                          ▼
                                   [Nextcloud 회사계정(원본)]
```

- X-Manager는 **서버에 동기화된 Nextcloud 폴더**를 직접 읽고 쓴다(기존 방식). 별도 Nextcloud API/OAuth 불필요.
- X-Manager가 파일을 쓰면 → 데스크톱 클라이언트가 회사계정으로 업로드 → 기존 공유 그대로 전파.
- 업로드가 주로 X-Manager를 거치므로 **양방향 동기화 충돌 최소화**.

## 8. 권한 모델

- **입구 통제**: 파일 브라우저 API는 요청을 거래처/주문 컨텍스트로 받아 **해당 엔티티의 기존 영업 RBAC 권한을 그대로 검사**.
- 생산팀 등 영업탭 미접근 팀은 API도 차단(권한 없음).
- v1은 별도 파일 권한 테이블 없이 **엔티티 권한 상속**. 추후 필요 시 하위 폴더별 팀 매핑(예: `04_생산·검사`는 생산팀 열람)으로 세분화.

## 9. 백엔드 설계

### 9-1. 경로 헬퍼 재정비 (`app/services/nextcloud_service.py`)
거래처 우선 트리에 맞춘 신규 헬퍼(기존 `build_customer_relpath`는 연도-중간이라 대체/보완):
- `build_customer_root(partner) -> str` : `수출/{국가}_{거래처}` 또는 `국내판매/{거래처}`
- `build_common_relpath(partner) -> str` : `{customer_root}/_공통`
- `build_order_relpath(partner, year, order_name) -> str` : `{customer_root}/{year}/{order_name}`
- `ensure_order_skeleton(order_relpath)` : 01~06 하위 폴더 생성(존재 시 그대로)
- 기존 `create_project_folder` / `save_file` / `sanitize` / `is_domestic` / `normalize_country_ko` 재사용.

### 9-2. 파일 브라우저 API (신규 라우터 `app/api/v1/cloud_files.py`, prefix **`/cloud-files`**) — ✅ 구현 완료
> ⚠️ `/files` 프리픽스는 **이미 첨부 다운로드 라우터가 사용** 중이라, 파일 허브는 **`/cloud-files`** 로 분리했다.
접근 통제: 라우터 등록 시 **`_guard("sales")`** 로 영업 권한 상속(생산팀 등 차단). 모든 경로는 `safe_abs()`로 베이스 내부 강제.

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/cloud-files/entry?scope=customer&customer_id=` | 거래처 루트 보장(ensure)·반환 + 목록 |
| GET | `/cloud-files/entry?scope=order&document_id=` | 주문 폴더 보장(01~06)·반환 + 목록 |
| GET | `/cloud-files/list?path=<relpath>` | 하위 폴더 목록(탐색·브레드크럼) |
| GET | `/cloud-files/preview?path=` | 이미지·PDF 인라인 스트리밍 |
| GET | `/cloud-files/download?path=` | 다운로드(attachment) |
| POST | `/cloud-files/upload?path=` (multipart) | 폴더에 파일 저장(동일명 자동 `(n)` 접미사) |
| POST | `/cloud-files/mkdir?path=&name=` | 하위 폴더 생성 |
| DELETE | `/cloud-files?path=` | 파일 삭제(폴더 삭제 불가) |

**응답(목록) 형태**: `[{ name, is_dir, size, mtime }]` + 현재 `path`(브레드크럼용).

**경로 안전장치(필수)**:
```python
def _safe_abs(relpath: str) -> Path:
    base = Path(settings.NEXTCLOUD_BASE_PATH).resolve()
    target = (base / relpath).resolve()
    if not str(target).startswith(str(base)):
        raise HTTPException(400, "잘못된 경로")   # ../ 탈출 차단
    return target
```

### 9-3. 엔티티 ↔ 폴더 매핑 (정확 매핑 원칙 §3 적용)
- 거래처/주문을 열 때 표준 폴더가 없으면 자동 생성(ensure). 경로는 거래처(국가·명)·PI번호에서 결정적으로 계산.
- **필수(변경됨)**: 최초 생성 시 그 경로를 **엔티티에 저장**한다 — `business_partner.nextcloud_folder`(거래처 루트), 주문은 향후 `sales_document`에 폴더 컬럼 추가. 이후엔 저장값만 사용 → **거래처명/PI 변경에도 링크 불변, 추측 없음.** (1a는 결정적 계산으로 동작, DB 저장은 1c에서 붙임)
- **레거시 수동 링크**: 기존 사람이 만든 폴더는 자동 매핑하지 않고, "기존 폴더 연결" UI로 사람이 1회 지정(향후).

### 9-4. 생성 문서 자동 사본
- X-Manager가 만드는 견적/PI/CI PDF를 해당 주문의 `02_영업문서`로 자동 저장(기존 활동폴더 저장 로직을 새 트리로 정렬).

## 12. 데이터 이관 계획 (43GB 레거시)

1. **오늘부터 신규 = 새 트리** (강제). 과거는 건드리지 않음.
2. X-Manager가 거래처/주문별 **표준 골격**을 미리 생성 → 이관 부담↓.
3. **활발한 거래처 우선** 점진 이관. 비활성 거래처는 레거시로 존치.
4. 레거시 폴더는 삭제하지 않음(추적/보존).

## 13. 거버넌스 / 운영 규칙

- **폴더 생성은 오직 X-Manager를 통해서만** — 직원의 임의(수기) 폴더 생성 금지(명명 일관성 유지의 핵심).
- **신규 파일은 X-Manager 통해 업로드** — Nextcloud 직접 진입은 예외적 상황만.
- 파일 접근·삭제는 X-Manager 권한을 따른다.
