# X-Manager 부품코드 · BOM 체계 재설계 작업 지시

> 이 문서는 별도 세션에서 확정된 설계 결론을 인계하는 문서다.
> **먼저 전체를 읽고, 7장의 작업 방식 규칙을 반드시 지킬 것.**

---

## 0. 당신의 역할과 이 작업의 성격

- 나는 엑스빔테크(방산 광커넥터 제조)의 COO 겸 CTO다. **세부 기술을 검토해줄 엔지니어가 사내에 없다.**
- 따라서 당신은 코드를 잘 짜는 것뿐 아니라, **왜 그렇게 하는지 한국어로 설명하고 내 승인을 받은 뒤 진행**해야 한다.
- X-Manager는 한 번에 완성하지 않는다. **모듈 단위로 조금씩 확장**한다. 이번 작업도 그 일부다.
- 이번 작업의 목표는 **부품코드 체계와 BOM 관리 구조를 재설계하고, 현행 시스템에 안전하게 이식하는 것**이다.

---

## 1. 배경 — 무엇이 문제인가

현재 X-Manager의 부품코드는 **코드 문자열 자체에 부품의 분류·용도·재질 등의 의미를 담는 방식(Intelligent Part Number)** 으로 설계되어 있다.

이로 인해 다음 문제가 발생하고 있다.

| 증상 | 원인 |
|---|---|
| 부품 등록 시마다 코드 규칙을 다시 확인해야 함 | 코드가 여러 의미 구간으로 나뉘어 외울 수 없음 |
| 어느 분류에 넣을지 판단이 어려움 | 분류 기준이 주관적 판단을 요구 |
| 담당자에게 물어봐야 코드가 나옴 | 채번이 사람 판단에 의존 (병목) |
| 코드를 봐도 부품을 구분하기 어려움 | 예외 규칙 누적으로 해독 불가 |
| 유사 부품이 중복 등록됨 | 검색이 어려워 기존 부품을 못 찾음 |

**핵심 진단:** 이것은 규칙이 덜 정교해서 생긴 문제가 아니라, "코드에 의미를 담는다"는 최초 설계 결정에서 필연적으로 따라온 결과다. 규칙을 더 다듬는 방향으로는 해결되지 않는다.

## 2. 확정된 설계 원칙 (임의 변경 금지)

아래는 이미 결정된 사항이다. 기술적으로 더 나은 대안이 있다고 판단되면 **먼저 근거를 제시하고 내 승인을 받은 뒤** 변경할 것. 임의로 바꾸지 말 것.

### 원칙 1 — 부품코드는 의미를 담지 않는다

```
형식:  [유형 접두어 1자리] - [전역 순번 5자리]

A-10247    광커넥터 어셈블리
P-10248    페룰
M-10249    SUS316 봉재
D-10250    조립도면
```

| 접두어 | 유형 | 판정 기준 (기계적) |
|---|---|---|
| `A` | Assembly (조립품) | 하위 BOM이 **있다** |
| `P` | Part (단품) | 하위 BOM이 **없다** |
| `M` | Material (원자재·부자재) | 수량 단위가 길이/중량/면적 |
| `D` | Document (도면·사양서) | 산출물 문서 |

- 순번은 **유형별로 나누지 않고 전역 통합 채번**. `A-10247` 다음이 `P-10248`인 것이 정상.
- 접두어는 **생성 시점에 확정, 이후 불변**. 단품(P)이 하위 BOM을 갖게 되면 코드는 그대로 두고 `item_type` 필드만 변경한다. 코드를 바꾸면 도면·계약서·고객 시스템이 어긋난다.
- **DB 내부 PK와 부품코드는 분리**한다. PK는 내부 정수, 부품코드는 표시용 unique 컬럼.
- 채번은 **시스템 자동**. 사용자는 유형만 선택한다.

### 원칙 2 — 가변 정보는 코드가 아니라 필드로

다음은 모두 **시간이 지나면 바뀌는 정보**이므로 코드에 넣지 않는다.

`제품구분(완제품/유닛/키트/부품)` · `판매여부` · `조달구분(자체가공/외주가공/구매)` · `협력사` · `리비전` · `분류` · `외부코드(NSN, 고객 P/N, 제조사 P/N)`

특히 **조달구분(외주 여부)을 코드 접두어에 넣지 말 것.** 내재화·이원화·업체변경이 수시로 발생하는 가장 가변적인 정보다.

### 원칙 3 — BOM 구조는 코드가 아니라 관계로 표현한다

부품 하나가 여러 제품에 서로 다른 위치로 들어가므로, 코드 문자열 하나에 계층 정보를 담는 것은 논리적으로 불가능하다.

- **BOM은 single-level로 저장**한다. 각 조립품이 자기 직계 자식만 갖는다.
- 다단계 전개는 **조회 시 재귀 쿼리로 계산**한다.
- **전개번호(`1.1.2`)는 저장하지 않는다.** 조회 시 동적 생성한다. 도면의 풍선번호와 같은 개념으로, 해당 BOM 안에서만 유효하다.

### 원칙 4 — 공정은 부품과 분리한다 (단, 반드시 등록한다)

- 외주 도금·열처리 등은 **자재가 아니라 공정**이다. `bom_lines`가 아니라 `process_routes`에 등록한다.
- 공정에는 **전사 코드를 부여하지 않는다.** `품목 + 순번(Seq 10, 20)`으로만 식별한다.
- 조회 화면에서는 품목 트리에 `OP10` 형태의 가상 노드로 **함께 표시**한다. 분리는 DB 안에서만 일어난다.
- **형상·기능을 바꾸는 외주 공정의 결과물은 별도 품번을 부여**한다.
  ```
  P-10248  페룰 (가공완료, 도금 전)   ← 외주 지급자재
     ↓ 외주 도금
  P-10310  페룰, Au 도금             ← 조립 투입품
  ```
  이유: 외주 지급/입고 재고 구분, 도금 사양별 파생품(Ni/Au/Cd) 관리, 방산 로트 추적성 확보.

### 원칙 5 — 원가는 4개 항목을 끝까지 분리해 집계한다

| 버킷 | 내용 | 발생 위치 | 방산원가 규칙 대응 |
|---|---|---|---|
| `material` | 재료비 | BOM | 재료비 |
| `labor` | 노무비 | 공정(자체) | 노무비 |
| `overhead` | 경비 | 공정(자체) | 경비 → 간접경비 |
| `subcontract` | 외주가공비 | 공정(외주) | 경비 → **직접경비 → 외주가공비** |

- **하위에서 발생한 외주비는 최상위까지 올라가도 `subcontract` 버킷에 남아야 한다.** 중간에 재료비로 합치면 원가 분석과 방산 원가검증 소명이 모두 불가능해진다.
- **수율(yield)** 은 하위 소요량과 외주 단가 **양쪽에** 적용한다. (불량품에도 도금비는 지불되므로)
- 사급 외주(외주업체가 자재까지 조달)는 단가를 `subcon_material_cost` / `subcon_process_cost`로 분해 저장한다.

### 원칙 6 — EBOM은 별도 트리로 만들지 않는다

- **MBOM 하나만 정확히 구축**한다.
- 고객 제출용 EBOM은 MBOM에서 공정과 내부 반제품(phantom)을 걸러낸 **뷰(View)** 로 생성한다.
- 두 트리를 따로 유지하면 설계 변경이 제조 쪽에 반영되지 않는 사고가 반드시 발생한다.

## 3. 목표 데이터 모델

현행 스키마를 확인한 뒤 아래를 기준으로 갭을 분석할 것. 컬럼명·타입은 기존 코드 컨벤션에 맞춰 조정해도 되지만, **구조와 분리 원칙은 유지**할 것.

```
items                          -- 품목 마스터
  id                PK, 내부 정수
  item_code         UNIQUE, 표시용  'A-10247'
  item_type         'A' | 'P' | 'M' | 'D'
  name              품명 (표기 규칙 적용: 명사, 수식어1, 수식어2)
  spec              규격
  uom               단위 (EA, kg, m ...)
  category_id       FK → categories
  revision          'A', 'B', 'C'
  make_buy          'MAKE' | 'SUBCON' | 'BUY'
  default_vendor_id FK → vendors
  is_sellable       bool
  product_class     '완제품' | '유닛' | '키트' | '부품'
  is_phantom        bool   -- EBOM 뷰에서 숨길 제조용 반제품
  status            '개발' | '양산' | '단종'
  legacy_code       기존 부품코드 보존 (마이그레이션용)
  created_at, updated_at

item_code_seq                  -- 전역 채번 시퀀스 (유형 무관 단일)

categories                     -- 계층형 분류 트리
  id, parent_id, name, path

item_xrefs                     -- 외부 코드 대응표
  id, item_id
  ref_type          'NSN' | 'CAGE' | 'CUSTOMER_PN' | 'MFR_PN' | 'DRAWING'
  ref_value, owner, note

bom_headers                    -- 품목별 BOM (single-level)
  id, item_id, bom_type ('MBOM'), revision
  effective_from, effective_to, status

bom_lines                      -- 직계 자식만
  id, bom_header_id, seq
  child_item_id     FK → items
  qty, uom
  yield_rate        기본 1.0
  ref_designator, note

process_routes                 -- 공정 (자체 + 외주)
  id, item_id, seq
  process_type      'INHOUSE' | 'SUBCON'
  operation_name    'CNC 가공', '외주 도금(Au)' ...
  work_center_id    자체일 때
  vendor_id         외주일 때
  setup_time, run_time
  labor_rate, overhead_rate
  subcon_process_cost      순수 가공비  → subcontract 버킷
  subcon_material_cost     사급 시 재료비 분해분 → material 버킷
  yield_rate
  contract_no, effective_from, effective_to   -- 원가 검증 증빙 연결

cost_versions                  -- 표준원가 버전
  id, name, base_date, status

item_costs                     -- roll-up 결과 스냅샷
  item_id, cost_version_id
  material_cost, labor_cost, overhead_cost, subcontract_cost
  total_cost, calculated_at
```

**Roll-up 알고리즘 요건**

```
cost(X) =
    Σ [ cost(child_i) × qty_i ÷ yield_i ]        -- 버킷별로 각각 누적
  + Σ [ 자체공정 j 의 노무비 ]                     → labor
  + Σ [ 자체공정 j 의 경비 ]                       → overhead
  + Σ [ 외주공정 j 의 가공비 ÷ yield ]             → subcontract
  + Σ [ 외주공정 j 의 사급 재료비 ÷ yield ]        → material
```

- 순환 참조 방어 필수 (경로 배열을 들고 다니며 자기 자신 재출현 시 에러)
- 메모이제이션 필수 (같은 부품이 여러 곳에 쓰임)
- setup 비용은 로트 사이즈로 배부

## 4. 첫 번째 작업 — 현행 시스템 조사 (코드 수정 금지)

**지금 당장 코드를 고치지 말 것.** 먼저 현행 시스템을 조사하고 리포트를 제출한 뒤 내 승인을 받는다.

### 조사 항목

1. **현행 부품코드 규칙**
   - 실제 코드 형식, 자릿수, 의미 구간 구성
   - 채번 로직이 어디에 구현되어 있는지 (파일·함수 위치)
   - 예외 처리·하드코딩된 규칙이 있는지

2. **현행 스키마**
   - 품목/BOM/공정 관련 테이블 전체 목록과 컬럼
   - PK·FK·인덱스·제약조건
   - 실제 등록된 데이터 규모 (품목 수, BOM 라인 수, 유형별 분포)

3. **BOM 저장 방식**
   - single-level인가, 전개된 형태로 저장하는가
   - 다단계 전개 로직이 있는가, 있다면 어디에
   - 순환 참조 방어가 있는가

4. **공정·외주 관련**
   - 공정 정보를 저장하는 구조가 존재하는가
   - 외주 정보가 어디에 어떻게 들어가 있는가
   - 원가 관련 컬럼·로직이 존재하는가

5. **부품코드 참조 지점 전수 조사**
   - 부품코드를 문자열로 파싱하는 코드가 있는가 (접두어 추출, substring 등)
   - 코드 규칙에 의존하는 정렬·필터·검증 로직
   - 프론트엔드에서 코드 형식을 검증하는 부분
   - 외부 연동(엑셀 업로드/다운로드, 리포트 출력)에서의 참조

6. **기술 스택 확인**
   - DB 종류·버전, 백엔드 프레임워크, 프론트엔드 스택
   - 마이그레이션 도구 사용 여부
   - 테스트 코드 존재 여부

### 제출할 리포트 형식

```
## 1. 현행 구조 요약
   (한국어로, 전문용어는 괄호 설명 병기)

## 2. 목표 모델과의 갭 분석
   | 항목 | 현행 | 목표 | 갭 크기 | 영향 범위 |

## 3. 위험 요소
   - 부품코드 파싱에 의존하는 코드 목록과 위치
   - 데이터 손실 가능 지점
   - 기존 화면이 깨질 수 있는 지점

## 4. 권장 전환 순서와 근거

## 5. 나에게 확인이 필요한 결정 사항
   (선택지와 각각의 장단점을 제시할 것)
```

## 5. 전환 원칙 (마이그레이션)

- **기존 부품코드는 절대 변경하지 않는다.** `legacy_code` 컬럼으로 보존하고, 신규 등록분부터 새 규칙을 적용한다. 두 체계를 병행하다 자연 소멸시킨다.
- **기존 테이블을 DROP 하거나 RENAME 하지 않는다.** 컬럼 추가 위주로 진행한다.
- 모든 DB 변경은 **마이그레이션 스크립트 + 롤백 스크립트 한 쌍**으로 작성한다.
- 마이그레이션 실행 전 **반드시 백업 절차를 안내**하고 내 확인을 받는다.
- 데이터 변환이 필요하면 **먼저 dry-run 모드로 결과를 보여주고** 승인 후 실제 실행한다.

## 6. 구현 순서 (모듈 단위, 각 단계마다 승인)

```
0단계  현행 조사 리포트                        ← 지금 할 일
1단계  스키마 확장 (컬럼 추가, 신규 테이블)
2단계  신규 채번 로직 + 품목 등록 화면
3단계  속성 검색 화면          ★ 이게 없으면 전환은 개악이 된다
4단계  BOM 재귀 전개 + 전개번호 조회 화면
5단계  공정(Routing) 등록 + 외주 관리
6단계  원가 roll-up 엔진 (4버킷)
7단계  EBOM 뷰 (고객 제출용)
8단계  기존 데이터 마이그레이션 / 병행 운영 종료
```

**3단계를 건너뛰지 말 것.** 유의미 코드를 버리는 대신 검색이 그 역할을 대신해야 한다. 검색이 준비되지 않은 상태에서 코드만 바꾸면 현장에서 반발이 온다.

## 7. 작업 방식 규칙 (반드시 준수)

1. **코드를 쓰기 전에 계획을 한국어로 설명하고 승인받는다.** 무엇을·왜·어떤 파일을 건드리는지 먼저 말한다.
2. **한 번에 한 모듈만.** 여러 단계를 묶어서 한꺼번에 진행하지 않는다.
3. **전문용어는 괄호로 한국어 설명을 병기한다.** (예: "재귀 CTE(계층 구조를 펼치는 SQL 기법)")
4. **각 단계 완료 후 동작 확인 방법을 알려준다.** 내가 직접 눈으로 확인할 수 있는 절차로.
5. **판단이 갈리는 지점에서는 임의로 정하지 말고 선택지를 제시한다.** 각 선택지의 장단점을 표로 정리할 것.
6. **기존 동작을 깨뜨릴 가능성이 있으면 먼저 경고한다.**
7. 방산 관련 규정·표준을 인용할 때는 **근거 출처를 명시**한다. 확실하지 않으면 "확인 필요"라고 표시한다.

---

## 8. 하지 말아야 할 것 (Anti-goals)

- ❌ 부품코드에 새로운 의미 구간을 추가하는 것
- ❌ 조달구분(외주/자체/구매)을 코드 접두어에 넣는 것
- ❌ 전개번호를 DB에 저장하는 것
- ❌ 원가 4버킷을 하나로 합치는 것
- ❌ 기존 부품코드를 일괄 변경하는 것
- ❌ EBOM과 MBOM을 별도 트리로 이중 관리하는 것
- ❌ 승인 없이 여러 모듈을 한꺼번에 구현하는 것
- ❌ 마이그레이션 스크립트를 롤백 없이 작성하는 것

## 9. 지금 시작할 것

**4장의 현행 시스템 조사만 수행하고, 지정된 형식으로 리포트를 제출하라. 코드는 수정하지 마라.**

조사 중 이 문서의 설계 원칙과 충돌하는 부분을 발견하면, 임의로 판단하지 말고 리포트의 "확인이 필요한 결정 사항"에 정리해서 올려라.
