## 1. 6개월 이상 미업데이트 영업 건 → 자동 '보류'

**이해:** 일정 기간(6개월) 동안 아무 변화가 없는 영업 건을 시스템이 자동으로 '보류'로 전환해, 죽은 건이 활성 목록을 채우지 않게 한다.

**결정 필요**
1. "업데이트" 기준: ① `updated_at`(상태·담당자 등 필드 변경) ② 마지막 **히스토리 로그**(코멘트/컨택 등) 작성일 — 어느 쪽?
   → 답변: 히스토리 로그
2. 대상 상태: 진행중/긴급/중요만 보류 전환? (완료·Drop·이미 보류는 제외 맞는지)
   → 답변: 진행중/긴급/중요만 보류로 전환(이미 완료, Drop 처리된건 의미 없음)
3. 실행 방식: 매일 1회 자동 배치(스케줄러 신규) vs 화면 열 때 계산?
   → 답변: 프로그램(시스템)에 부하가 없다면 매일 1회 자동
4. 자동 전환 시 히스토리 로그("6개월 미활동으로 자동 보류")를 남길까?
   → 답변: 로그를 어디에 남긴다는 건지?
   → (Claude) 각 영업 건의 **진행 상황 히스토리 타임라인**(코멘트·문서생성이 뜨는 그곳, SalesActivityLog).
     자동 보류 시 "180일 미활동으로 자동 보류" 항목이 찍혀 이유를 알 수 있음. **남기기 추천.**
   → 최종 답변:
5. 기간 정의: 정확히 180일 vs 달력상 6개월?
   → 답변: 정확히 180일

**결정 필요 (2차) — 위 답변 반영 후 추가로 정할 것**
> 현재 상태값(확인함): `IN_PROGRESS`(진행중) / `WAITING`(대기) / `COMPLETED`(완료) / `ON_HOLD`(보류) / `DROPPED`(무산).
> 긴급·중요는 **상태가 아니라 플래그**(is_urgent / is_important) — 진행중 건에 표시로 붙음.

6. 대상 상태 확정: **진행중(IN_PROGRESS)만** 보류 전환? **대기(WAITING)도 포함**? (완료·보류·무산은 제외 확정)
   → 답변: 대기건도 동일 취급
7. 활동 로그가 0개인 건(코멘트/문서 기록 없음): **건 생성일(created_at)**을 마지막 활동일로 간주 → 생성 후 180일 미활동이면 보류. OK?
   → 답변: OK
8. 배치 실행 시각/방식: 매일 **새벽 4시(KST)**, 기존 백업과 동일하게 **Windows 작업 스케줄러 + python 스크립트**(백엔드 프로세스와 독립, 견고). OK?
   → 답변: OK
9. 최초 1회 실행 시 기존 오래된 건들이 **한꺼번에 대량 보류**될 수 있음 — 의도된 동작이니 OK? (원하면 최초엔 대상 목록만 리포트 → 수동 승인 후 적용도 가능)
   → 답변: OK
10. 보류된 건에 새 활동(코멘트 등)이 생기면 **자동으로 진행중 복귀** vs **수동 복귀**? (추천: 수동 — 자동 복귀는 예측 어려움)
    → 답변: 수동 복귀
11. 자동 보류 시 담당자에게 **인앱 알림** 보낼지? (기본: 안 보냄 — 노이즈 우려)
    → 답변: 안보냄

### ✅ 확정 스펙 (LOCKED — 구현 기준)
- **대상**: 상태가 `IN_PROGRESS`(진행중) 또는 `WAITING`(대기) 인 건. (완료·보류·무산 제외)
- **판정 기준일** = 그 건의 **마지막 히스토리 로그(SalesActivityLog) 작성일**. 로그가 0개면 **건 생성일(created_at)**.
- **조건**: 기준일이 **오늘 - 180일** 이전이면 → 상태를 `ON_HOLD`(보류)로 변경.
- **히스토리 로그**: 전환 시 해당 건 타임라인에 `"180일 미활동으로 자동 보류"` 로그 1건 추가(log_type 신규, 예: `AUTO_HOLD`). *(4번 최종답변 대기 — 남기기로 진행)*
- **복귀**: 자동 복귀 없음(수동). 보류 후 새 활동이 생겨도 상태는 그대로 → 담당자가 수동으로 진행중 전환.
- **실행**: 매일 **04:00 KST**, **Windows 작업 스케줄러 + python 스크립트**(백엔드 프로세스와 독립). 로그는 스크립트 실행 결과 파일에 append.
- **최초 실행**: 기존 오래된 건 대량 보류 허용(리포트 후 승인 절차 없이 바로 적용).
- **알림**: 담당자 인앱 알림 없음.

## 2. 상태 / 긴급·중요 필터를 캘린더식 다중선택으로

**이해(현재 확인함):** 지금 상태는 **단일 선택 드롭다운**(`filters.status` 하나)이라 한 번에 한 상태만 본다. 이를 **캘린더 이벤트 유형 토글처럼** 상태 칩을 여러 개 켤 수 있게 → 하나만 켜면 그것만, 여러 개 켜면 합쳐서 표시. 긴급/중요도 현재 "긴급+중요" 고정 묶음인데 **각각 독립 토글**로 (긴급만 / 중요만 / 둘 다) 선택 가능하게.

**결정 필요**
1. 토글 대상 상태 전체: 진행중·완료·보류·Drop 전부 칩으로? (신규 '보류' 포함)
   → 답변: 보류까지 하면 너무 많아지지 않을까.. 완료, 보류, Drop을 어떻게 처리할지 논의 필요
2. 긴급/중요와 상태의 조합 방식: 상태 필터 ∩ 플래그 필터(예: "진행중이면서 긴급") vs 별개 축?
   → 답변: 별개 축으로 둘 다 선택하면 긴급&중요 건으로 볼 수 있으니 괜찮을듯
3. 기본값(첫 진입): 전체 표시(전부 켜짐) vs 진행중만?
   → 답변: 기본값은 전부 켜짐
4. 긴급·중요 건 1페이지 최상단 정렬은 그대로 유지?
   → 답변: 그대로 유지
5. (참고) 백엔드 API가 `status` 단일 파라미터라 다중 배열을 받도록 함께 수정 필요.

### ✅ 확정 스펙 (LOCKED — 구현 기준)
- **상태 칩(5개, 합집합 OR)**: 진행중·대기·보류·완료·무산. 켜진 상태들의 **합집합** 표시.
  - **기본 ON = 진행중·대기·보류** (완료·무산은 OFF → 눌러야 보임). 칩은 5개 다 노출.
  - (엣지) 상태를 **하나도 안 켜면** 결과 없음(캘린더 토글과 동일).
- **우선도 칩(2개, 좁히기 필터)**: 긴급 / 중요.
  - **기본 = 둘 다 OFF = 우선도 무관 전체 표시**(정상·긴급·중요 다 보임). ← "전부 보기"의 기본 상태.
  - 긴급만 ON → 긴급 건 / 중요만 ON → 중요 건 / **둘 다 ON → 긴급이거나 중요(OR)**.
  - **정렬**: 결과 안에서 **긴급&중요(둘 다 표시된) 건을 1페이지 최상단**에 노출(기존 유지).
- **축 결합**: 최종 = (상태 합집합) **AND** (우선도 필터). 상태·우선도는 별개 축.
- **백엔드**: 리스트 API가 `status` 다중값 + `urgent`/`important` 플래그 필터를 받도록 수정.
