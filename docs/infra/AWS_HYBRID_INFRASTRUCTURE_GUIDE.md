## 1. 개요

### 1.1 Hybrid 구성이란?

**사내 서버(Primary)** + **AWS 클라우드(Standby)** 조합으로 운영하는 방식입니다.

| 구분 | 역할 | 설명 |
|------|------|------|
| **사내 서버** | Primary (주) | 평상시 모든 트래픽 처리 |
| **AWS 서버** | Standby (대기) | 사내 서버 장애 시 자동 전환 |
| **AWS RDS** | 공유 DB | 양쪽 서버가 동일한 DB 사용 |

### 1.2 왜 Hybrid 구성인가?

| 장점 | 설명 |
|------|------|
| **비용 절감** | 사내 서버가 메인 → 클라우드 비용 최소화 |
| **데이터 안전** | DB가 클라우드 → 자동 백업, 장애 복구 |
| **고가용성** | 장애 시 자동 전환 → 서비스 중단 최소화 |
| **확장성** | 필요시 클라우드 스펙 업그레이드 가능 |

### 1.3 HTTPS만 필요한 경우 vs Hybrid

| 목표 | AWS 필요 여부 | 방법 |
|------|:-:|------|
| **HTTPS 외부 접속만** | **불필요** | Caddy + 메일플러그 DNS만으로 가능 (비용 0원) |
| HTTPS + 장애 자동 전환 | 필요 | Hybrid 구성 |
| HTTPS + 클라우드 DB 백업 | 필요 | Hybrid 구성 |
| HTTPS + 장애 전환 + DB 백업 + 모니터링 | 필요 | **Hybrid 구성 (본 가이드)** |

### 1.4 다른 옵션과 비교

| 구성 | 월 비용 | 안정성 | 관리 난이도 |
|------|---------|--------|------------|
| 사내 서버만 (HTTPS) | 0원 | ★★☆☆☆ | 쉬움 |
| **Hybrid (권장)** | **~2.1~4.6만원** | **★★★★☆** | **중간** |
| AWS 단독 | ~8만원 | ★★★★★ | 쉬움 |

## 2. 기존 인프라 현황

### 2.1 현재 구조

```
외부 사용자
  → 메일플러그 DNS (서브도메인 관리)
    → 회사 공인 IP (게이트웨이)
      → Caddy (리버스 프록시 + SSL 자동 발급)
        → 각 내부 서비스 (메일, ERP, X-MANAGER 등)
```

### 2.2 활용하는 기존 인프라

| 항목 | 현재 상태 | Hybrid 전환 후 |
|------|----------|---------------|
| **DNS** | 메일플러그에서 서브도메인 관리 | X-MANAGER 서브도메인만 Route 53으로 위임 |
| **SSL 인증서** | Caddy가 자동 발급/갱신 (Let's Encrypt) | 그대로 유지 (ACM 불필요) |
| **리버스 프록시** | Caddy | 그대로 유지 (Nginx 불필요) |
| **도메인** | 기존 회사 도메인 사용 | 신규 도메인 구매 불필요 |

### 2.3 Caddyfile 보안 헤더 (권장)

```
xm.회사도메인.com {
    reverse_proxy 서버내부IP:8000

    header {
        X-Content-Type-Options "nosniff"
        X-Frame-Options "SAMEORIGIN"
        Strict-Transport-Security "max-age=31536000; includeSubDomains"
        Referrer-Policy "strict-origin-when-cross-origin"
        -Server
    }
}
```

| 헤더 | 역할 |
|------|------|
| `X-Content-Type-Options` | 파일 형식 위조 방지 |
| `X-Frame-Options` | iframe 삽입(클릭재킹) 차단 |
| `Strict-Transport-Security` | HTTPS 강제 |
| `Referrer-Policy` | 주소 정보 유출 제한 |
| `-Server` | 서버 소프트웨어 정보 숨김 |

### 3.2 DNS 위임 구조

```
메일플러그 DNS:
  mail.회사.com  → A 레코드 → 회사 IP        (기존 유지)
  erp.회사.com   → A 레코드 → 회사 IP         (기존 유지)
  xm.회사.com    → NS 레코드 → Route 53 NS 4개  (위임)

Route 53 (xm.회사.com만 관리):
  xm.회사.com → Failover 라우팅
    Primary:   회사 공인 IP (사내 서버)
    Secondary: Lightsail 고정 IP (대기 서버)
```

> 기존 서비스(메일, ERP 등)에 영향 없이 X-MANAGER 서브도메인만 Route 53으로 위임합니다.

### 3.3 장애 시나리오

```
[정상 상태]
사용자 → Route 53 → 사내 서버 (게이트웨이 → Caddy → X-MANAGER) → RDS

[사내 서버 장애 발생]
1. Route 53 Health Check가 사내 서버 응답 없음 감지 (30초 x 3회 = 90초)
2. DNS가 자동으로 AWS Lightsail(Standby)로 전환
3. 사용자 → Route 53 → AWS Lightsail (Caddy → X-MANAGER) → RDS

[사내 서버 복구 후]
1. Health Check가 사내 서버 정상 감지
2. DNS가 다시 사내 서버(Primary)로 전환
3. 사용자 → Route 53 → 사내 서버 (게이트웨이 → Caddy → X-MANAGER) → RDS
```

## 4. AWS 서비스별 상세 설명

### 4.1 Amazon Route 53 (DNS Failover)

#### 용도
- **서브도메인 DNS 관리**: xm.회사도메인.com의 DNS 레코드 관리
- **Health Check**: 서버 상태 주기적 확인 (30초 간격)
- **Failover**: 장애 감지 시 자동으로 대기 서버로 전환

#### 왜 필요한가?
- 메일플러그 DNS는 장애 감지/자동 전환 기능이 없음
- Route 53은 서버 상태를 모니터링하고 자동 전환 가능
- 기존 서비스에 영향 없이 X-MANAGER 서브도메인만 관리

#### AWS 콘솔 경로
```
AWS 콘솔 → Route 53 → 호스팅 영역
```

#### 설정 항목
| 항목 | 설정 값 |
|------|---------|
| 호스팅 영역 | 서브도메인 입력 (예: xm.회사도메인.com) |
| 유형 | 퍼블릭 호스팅 영역 |
| Health Check 프로토콜 | HTTPS |
| Health Check 경로 | /api/health |
| 요청 간격 | 30초 |
| 실패 임계값 | 3회 (90초 후 전환) |

#### 가격
| 항목 | 월 비용 |
|------|---------|
| 호스팅 영역 | $0.50 (~700원) |
| Health Check (HTTPS) | $0.50 (~700원) x 2개 |
| DNS 쿼리 | ~$0.10 (소규모) |
| **소계** | **~$1.60 (~2,200원)** |

---

### 4.2 Amazon Lightsail (대기 서버)

#### 용도
- 사내 서버 장애 시 서비스를 대신 처리하는 **대기 서버**
- Caddy + Docker 기반으로 X-MANAGER 애플리케이션 실행

#### 왜 필요한가?
- 사내 서버만 운영 시 장애 = 서비스 중단
- 대기 서버가 있으면 장애 시에도 서비스 지속 가능

#### EC2 vs Lightsail
| 항목 | EC2 | Lightsail |
|------|-----|-----------|
| 복잡도 | 높음 (세부 설정 많음) | **낮음 (간편)** |
| 가격 예측 | 어려움 (종량제) | **쉬움 (고정 요금)** |
| 기능 | 매우 다양 | 기본적 기능 |
| **추천** | 대규모 | **소규모~중규모** |

#### AWS 콘솔 경로
```
https://lightsail.aws.amazon.com
```

#### 설정 항목
| 항목 | 권장 선택 |
|------|----------|
| 플랫폼 | Linux/Unix |
| 블루프린트 | OS Only → Ubuntu 22.04 LTS |
| 인스턴스 플랜 | $10/월 (2GB RAM, 1 vCPU, 60GB SSD) |
| 리전 | 아시아 태평양 (서울) ap-northeast-2 |
| 고정 IP | 생성 후 연결 (무료) |

#### 가격
| 플랜 | RAM | vCPU | SSD | 월 비용 |
|------|-----|------|-----|---------|
| 최소 | 1GB | 1 | 40GB | $5 (~7,000원) |
| **권장** | **2GB** | **1** | **60GB** | **$10 (~14,000원)** |
| 여유 | 4GB | 2 | 80GB | $20 (~28,000원) |

### 4.3 Amazon RDS (공유 데이터베이스)

#### 용도
- PostgreSQL 데이터베이스를 클라우드에서 운영
- 사내 서버와 AWS 서버가 **동일한 DB를 공유**

#### 왜 필요한가?
- DB가 사내에 있으면 → 사내 서버 장애 시 데이터 접근 불가
- DB가 클라우드에 있으면 → 어느 서버든 동일한 데이터 접근 가능
- **데이터 동기화 문제 해결** (동기화할 필요 없음)

#### 자체 설치 vs RDS
| 항목 | 자체 설치 (EC2에 PostgreSQL) | RDS |
|------|------------------------------|-----|
| 설치/설정 | 직접 해야 함 | AWS가 해줌 |
| 백업 | 직접 설정 | **자동 백업** |
| 업데이트 | 직접 해야 함 | **자동 업데이트** |
| 장애 복구 | 직접 해야 함 | **자동 복구** |
| 가격 | 저렴 | 약간 비쌈 |
| **추천** | DB 전문가 있을 때 | **일반적인 경우** |

#### AWS 콘솔 경로
```
AWS 콘솔 → RDS → 데이터베이스 생성
```

#### 설정 항목
| 항목 | 권장 선택 |
|------|----------|
| 엔진 | PostgreSQL |
| 버전 | PostgreSQL 15.x (최신 안정 버전) |
| 템플릿 | 프리 티어 (1년간) 또는 프로덕션 |
| 인스턴스 클래스 | db.t3.micro ($15/월, 프리 티어 대상) 또는 db.t3.small ($30/월) |
| 스토리지 | 범용 SSD (gp2), 20GB |
| Multi-AZ | 아니오 (비용 절감, 필요시 활성화) |
| **퍼블릭 액세스** | **예** (사내 서버 접속 필요) |
| VPC 보안그룹 | 사내 IP + AWS Lightsail IP만 허용 |

#### 가격
| 인스턴스 | RAM | 스토리지 | 월 비용 | 비고 |
|----------|-----|----------|---------|------|
| db.t3.micro | 1GB | 20GB | ~$15 (~21,000원) | **프리 티어 1년 무료** |
| **db.t3.small** | **2GB** | **20GB** | **~$30 (~42,000원)** | 권장 |
| db.t3.medium | 4GB | 50GB | ~$70 (~98,000원) | 여유 |

### 4.4 Amazon S3 (파일 저장소)

#### 용도
- 첨부파일, 이미지, 문서 등 **파일 저장**
- 사내 서버와 AWS 서버가 동일한 파일 접근

#### 왜 필요한가?
- 파일이 사내 서버에만 있으면 → 장애 전환 시 파일 접근 불가
- S3에 저장하면 → 어느 서버든 동일한 파일 접근 가능

#### AWS 콘솔 경로
```
AWS 콘솔 → S3 → 버킷 만들기
```

#### 설정 항목
| 항목 | 권장 선택 |
|------|----------|
| 버킷 이름 | xmanager-files (전 세계 고유해야 함) |
| 리전 | 아시아 태평양 (서울) |
| 퍼블릭 액세스 | 모든 퍼블릭 액세스 차단 |
| 버전 관리 | 활성화 (실수로 삭제해도 복구 가능) |

#### 가격
| 항목 | 단가 | 예상 비용 (50GB 기준) |
|------|------|----------------------|
| 스토리지 | $0.025/GB | ~$1.25 |
| 요청 (PUT) | $0.005/1,000건 | ~$0.10 |
| 요청 (GET) | $0.0004/1,000건 | ~$0.05 |
| **소계** | | **~$1.5 (~2,100원)** |

### 4.5 Amazon CloudWatch (모니터링) - 선택

#### 용도
- 서버, DB, 네트워크 등의 **상태 모니터링**
- 임계값 초과 시 **알림 발송** (이메일)

#### 왜 필요한가?
- 문제가 발생하기 전에 미리 감지
- 장애 발생 시 빠른 대응 가능

#### AWS 콘솔 경로
```
AWS 콘솔 → CloudWatch → 경보
```

#### 권장 알림 설정
| 지표 | 조건 | 설명 |
|------|------|------|
| CPU 사용률 | > 80% (5분) | 서버 과부하 감지 |
| 메모리 | > 90% | 메모리 부족 감지 |
| 디스크 | > 85% | 스토리지 부족 감지 |
| RDS 연결 수 | > 80% | DB 연결 포화 감지 |
| Health Check 실패 | > 1회 | 서버 장애 감지 |

#### 가격
| 항목 | 월 비용 |
|------|---------|
| 기본 모니터링 (5분 간격) | 무료 |
| 상세 모니터링 (1분 간격) | $3~5 |
| 경보 | $0.10/개 |
| **소계** | **무료~$5 (~7,000원)** |

### 4.6 AWS WAF (웹 방화벽) - 선택, 초기 불필요

#### 용도
- **SQL Injection**, **XSS** 등 웹 공격 차단
- 악성 봇, 스크래핑 방어

#### 초기에 불필요한 이유
- 사내 직원 위주 소규모 사용 → 공격 대상 가능성 낮음
- 부품/거래처 정보 → 개인정보 아님
- 기본 방화벽(Security Group)으로 IP 제한만으로 충분
- 필요 시 언제든 AWS 콘솔에서 활성화 가능

#### 나중에 추가 고려 시점
- 외부 고객이 직접 접속하는 서비스로 확장할 때
- 비정상 접근 로그가 자주 발견될 때
- 회사 보안 정책상 필수 요구 시

## 6. 구축 순서

### 6.0 사전 준비

```
□ AWS 계정 생성 (https://aws.amazon.com) - 플랜: Basic (무료)
□ 결제 수단 등록 (신용카드)
□ 루트 계정 MFA 활성화 (Google Authenticator)
□ IAM 사용자 생성 (AdministratorAccess 권한)
□ 이후 모든 작업은 IAM 사용자로 로그인
```

### 6.1 단계별 구축 (7단계)

```
[1단계: Route 53 서브도메인 위임]

  ① AWS Route 53 → 호스팅 영역 → "호스팅 영역 생성"
     → 도메인 이름: xm.회사도메인.com
     → 유형: 퍼블릭 호스팅 영역
     → 생성 후 NS 레코드 4개 확인

  ② 메일플러그 DNS 설정
     → xm.회사도메인.com의 기존 A 레코드 삭제
     → xm.회사도메인.com에 NS 레코드 추가
     → 값: Route 53에서 받은 NS 4개 입력
       예: ns-123.awsdns-45.com
           ns-678.awsdns-90.net
           ns-111.awsdns-22.org
           ns-333.awsdns-44.co.uk

  → 결과: xm.회사도메인.com의 DNS를 Route 53이 관리
  → 다른 서비스(메일, ERP 등)에 영향 없음
  → 결제: $0.50/월 (~700원)
```

```
[2단계: RDS 데이터베이스 생성]

  ① AWS RDS → "데이터베이스 생성"
     → 엔진: PostgreSQL 15.x
     → 템플릿: 프리 티어
     → 인스턴스: db.t3.micro (프리 티어 1년 무료)
     → 스토리지: 20GB gp2
     → 리전: 서울 (ap-northeast-2)
     → 퍼블릭 액세스: 예
     → 보안 그룹: 회사 공인 IP + Lightsail IP만 허용

  ② 생성 완료 후
     → 엔드포인트 주소 확인
       예: xmanager-db.xxxxx.ap-northeast-2.rds.amazonaws.com
     → 로컬 DB 데이터를 RDS로 마이그레이션
       pg_dump -h localhost -U postgres -d xmanager > backup.sql
       psql -h RDS엔드포인트 -U postgres -d xmanager < backup.sql
     → 연결 테스트

  → 결제: ~$15/월 (프리 티어 1년간 인스턴스 무료, 스토리지만 과금)
```

```
[3단계: S3 파일 저장소 생성]

  ① AWS S3 → "버킷 만들기"
     → 버킷 이름: xmanager-files
     → 리전: 서울
     → 퍼블릭 액세스: 모두 차단
     → 버전 관리: 활성화

  ② IAM에서 S3 접근용 사용자/정책 생성
     → 액세스 키 발급
     → 애플리케이션에 S3 연동 코드 추가

  ③ 기존 로컬 파일 → S3로 마이그레이션

  → 결제: ~$1.5/월 (사용량 기반)
```

```
[4단계: 사내 서버 설정 변경]

  ① X-MANAGER 환경변수 변경
     → DB 연결: 로컬 DB → RDS 엔드포인트로 변경
     → 파일 저장: 로컬 경로 → S3로 변경

  ② Caddyfile에 X-MANAGER 서브도메인 추가
     → xm.회사도메인.com 블록 추가
     → 보안 헤더 설정
     → Caddy가 SSL 자동 발급

  ③ 게이트웨이 설정
     → 80, 443 포트 → Caddy 서버로 포워딩 (이미 되어있으면 생략)

  ④ 헬스체크 확인
     → https://xm.회사도메인.com/api/health 접속 테스트
     → {"status": "healthy", "database": "connected"} 응답 확인

  → 결제: 없음
```

```
[5단계: Lightsail 대기 서버 생성]

  ① AWS Lightsail → "인스턴스 생성"
     → 리전: 서울 (ap-northeast-2)
     → OS: Ubuntu 22.04
     → 플랜: $10/월 (2GB RAM, 1 vCPU, 60GB SSD)

  ② 고정 IP 연결
     → Lightsail → 네트워킹 → 고정 IP 생성 → 인스턴스에 연결

  ③ 서버 환경 구성
     → Docker 설치
     → Caddy 설치
     → X-MANAGER 배포 (사내 서버와 동일한 설정)
     → RDS, S3 연결 설정 (사내 서버와 동일한 환경변수)
     → Caddy에 SSL 설정

  ④ 테스트
     → Lightsail IP로 직접 접속하여 X-MANAGER 정상 동작 확인

  → 결제: $10/월 (~14,000원)
```

```
[6단계: Failover + Health Check 설정]

  ① Route 53 → 상태 검사 → "상태 검사 생성"

     사내 서버 Health Check:
     → 프로토콜: HTTPS
     → IP 주소: 회사 공인 IP
     → 경로: /api/health
     → 요청 간격: 30초 (표준)
     → 실패 임계값: 3회

     Lightsail Health Check:
     → 프로토콜: HTTPS
     → IP 주소: Lightsail 고정 IP
     → 경로: /api/health
     → 요청 간격: 30초 (표준)
     → 실패 임계값: 3회

  ② Route 53 → 호스팅 영역 → xm.회사도메인.com

     A 레코드 생성 (Primary):
     → 값: 회사 공인 IP
     → 라우팅 정책: 장애 조치 (Failover)
     → 레코드 유형: 기본 (Primary)
     → 상태 검사: 사내 서버 Health Check 연결

     A 레코드 생성 (Secondary):
     → 값: Lightsail 고정 IP
     → 라우팅 정책: 장애 조치 (Failover)
     → 레코드 유형: 보조 (Secondary)
     → 상태 검사: Lightsail Health Check 연결

  ③ Failover 테스트
     → 사내 서버의 X-MANAGER 중지
     → 90초 후 xm.회사도메인.com 접속 → Lightsail에서 응답 확인
     → 사내 서버 재시작 → 다시 사내 서버로 전환 확인

  → 결제: Health Check $0.50 x 2 = $1.00/월 (~1,400원)
```

```
[7단계: CloudWatch 모니터링 설정 (선택)]

  ① AWS CloudWatch → "경보 생성"
     → RDS CPU 사용률 > 80% 알림
     → RDS 연결 수 > 80% 알림

  ② AWS SNS → 토픽 생성
     → 이메일 알림 설정 (관리자 이메일)
     → 이메일 구독 확인

  ③ 테스트 알림 발송

  → 결제: 기본 모니터링 무료, 상세 시 ~$3~5/월
```

## 8. 로컬 데이터 접근 및 백업

### 8.1 RDS 데이터 접근 (로컬에서)

AWS에 DB를 올려도 로컬에서 자유롭게 접근/분석/백업이 가능합니다.

#### 무료 GUI 도구
| 도구 | 용도 |
|------|------|
| **pgAdmin** (로컬 설치) | PostgreSQL 전용 GUI, 쿼리/분석/백업 |
| **DBeaver** (로컬 설치) | 범용 DB 클라이언트, 엑셀 내보내기 |

#### 접속 설정
```
호스트: xmanager-db.xxxxx.ap-northeast-2.rds.amazonaws.com
포트: 5432
데이터베이스: xmanager
사용자: postgres
비밀번호: (설정한 비밀번호)
```

### 8.2 백업 방법

#### AWS 자동 백업
```
RDS → 데이터베이스 → 수정 → 백업 보존 기간: 7일 (최대 35일)
→ 매일 자동 스냅샷 생성
→ DB 크기만큼 무료 (20GB DB → 20GB 백업 무료)
```

#### 로컬 수동 백업
```bash
# 1회 백업
pg_dump -h RDS엔드포인트 -U postgres -d xmanager > backup_20260303.sql

# 로컬 DB로 복원
psql -h localhost -U postgres -d xmanager_local < backup_20260303.sql
```

#### 자동 주기 백업 (Windows 작업 스케줄러)
```bash
# backup.bat
pg_dump -h RDS엔드포인트 -U postgres -d xmanager > C:\backups\xmanager_%date%.sql
```
```
Windows 작업 스케줄러 → 새 작업 만들기
→ 트리거: 매일 새벽 3시
→ 동작: backup.bat 실행
```
