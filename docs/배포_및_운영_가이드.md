# X-Manager 배포 및 운영 가이드

## 개요

이 문서는 X-Manager를 운영 환경에서 실행하고, 개발과 운영을 병행하는 방법을 설명합니다.

**최종 업데이트**: 2026-01-16

---

## 1. 환경 구성

### 1.1 환경 분리 구조

```
📁 X-MANAGER_R0.1/
├── 📁 backend/
│   ├── .env                 ← 기본 설정 (미사용)
│   ├── .env.production      ← 운영 환경 설정
│   └── .env.development     ← 개발 환경 설정
├── 📁 frontend/
├── 📁 storage/              ← 운영 파일 저장소
├── 📁 storage_dev/          ← 개발 파일 저장소
├── 📁 scripts/              ← 유틸리티 스크립트
├── start-prod.bat           ← 운영 서버 실행
└── start-dev.bat            ← 개발 서버 실행
```

### 1.2 포트 구성

| 환경 | 백엔드 | 프론트엔드 | DB |
|------|--------|------------|-----|
| 운영 | localhost:8000 | localhost:5173 | xmanager |
| 개발 | localhost:8001 | localhost:5174 | xmanager_dev |

### 1.3 서버 실행 시 CMD 창

서버 실행 시 **2개의 CMD 창**이 열립니다:
- **Backend** 창: 백엔드 서버 (uvicorn)
- **Frontend** 창: 프론트엔드 서버 (vite)

> ⚠️ CMD 창을 닫으면 해당 서버가 종료됩니다. 서버를 유지하려면 창을 열어두세요.

## 3. 서버 실행

### 3.1 운영 서버 실행

```
start-prod.bat 더블클릭
```

- 백엔드: http://localhost:8000
- 프론트엔드: http://localhost:5173
- DB: xmanager
- API 문서: http://localhost:8000/docs

### 3.2 개발 서버 실행

```
start-dev.bat 더블클릭
```

- 백엔드: http://localhost:8001 (자동 리로드 활성화)
- 프론트엔드: http://localhost:5174
- DB: xmanager_dev
- API 문서: http://localhost:8001/docs

### 3.3 동시 실행

운영 서버와 개발 서버를 **동시에** 실행할 수 있습니다.
- 운영: 데이터 입력 작업
- 개발: 새 기능 개발/테스트

### 3.4 서버 상태 확인

현재 실행 중인 서버 확인 (CMD에서):

```cmd
netstat -ano | findstr "8000 8001 5173 5174"
```

프로세스로 확인:
```cmd

```

### 3.5 서버 종료

**방법 1**: CMD 창 닫기

**방법 2**: 프로세스 직접 종료 (PID로)

## 4. 코드 변경 유형별 배포 절차

코드 변경은 크게 두 가지로 나뉩니다:

| 변경 유형 | 예시 | 운영 DB 마이그레이션 |
|-----------|------|---------------------|
| **코드만 변경** | UI 수정, 버그 수정, API 로직 변경 | 불필요 |
| **DB 스키마 변경** | 테이블/컬럼 추가, 모델 변경 | **필수** |

---

### 4.1 코드만 변경하는 경우 (DB 변경 없음)

```
1. 개발 서버에서 코드 수정 및 테스트
2. 운영 서버 재시작
```

**개발 서버**: 코드 수정 시 자동 반영 (`--reload` 옵션)

**운영 서버**: 수동 재시작 필요
1. 운영 서버 창 닫기
2. `start-prod.bat` 다시 실행

---

### 4.2 DB 스키마가 변경되는 경우 (⚠️ 중요)

DB 구조가 바뀌면 **반드시 운영 DB에도 마이그레이션을 적용**해야 합니다.
그렇지 않으면 운영 서버 재시작 시 에러가 발생합니다.

```
⚠️ 잘못된 순서 (에러 발생!)
───────────────────────────
코드 변경 + 마이그레이션 생성
       ↓
개발 DB에만 적용
       ↓
운영 서버 재시작 → 에러! (컬럼이 없음)
```

```
✅ 올바른 순서
───────────────────────────
1. 코드 변경 + 마이그레이션 파일 생성
2. 개발 DB에 적용 → 테스트
3. 운영 DB에 적용 ← 필수!
4. 운영 서버 재시작
```

#### 단계별 명령어

**1단계: 마이그레이션 파일 생성**
```bash
cd backend
alembic revision --autogenerate -m "설명"
```

**2단계: 개발 DB에 적용 (테스트)**
```bash
set APP_ENV=development
alembic upgrade head
```

**3단계: 개발 서버에서 테스트**
- http://localhost:5174 에서 기능 확인

**4단계: 운영 DB에 적용** ⚠️
```bash
set APP_ENV=production
alembic upgrade head
```

**5단계: 운영 서버 재시작**
```
start-prod.bat 다시 실행
```

> 💡 마이그레이션은 기존 데이터를 유지하면서 스키마만 변경합니다.

---

### 4.3 체크리스트

운영 서버 재시작 전 확인:

- [ ] 마이그레이션 파일이 새로 생성되었는가?
  - 생성됨 → 운영 DB에 `alembic upgrade head` 필수
  - 없음 → 바로 재시작 가능
- [ ] 개발 서버에서 테스트 완료했는가?
- [ ] 운영 DB 백업했는가? (권장)

## 5. 백업 시스템

### 5.1 백업 정책

| 기간 | 보관 방식 |
|------|-----------|
| 24시간 이내 | 모든 백업 유지 (시간별) |
| 1~30일 | 하루 1개만 유지 (00시 백업) |
| 30일 이후 | 자동 삭제 |

### 5.2 백업 위치

```
📁 storage/backups/
├── xmanager_2026-01-16_09-00.dump  ← 최근 24시간
├── xmanager_2026-01-16_10-00.dump
└── 📁 daily/
    ├── xmanager_2026-01-15_00-00.dump  ← 1~30일
    └── xmanager_2026-01-14_00-00.dump
```

### 5.3 자동 백업 설정 (1회)

```
scripts\setup-backup-schedule.bat 우클릭 → "관리자 권한으로 실행"
```

등록 후 자동으로:
- 매 시간: 백업 생성
- 매일 00:30: 오래된 백업 정리

### 5.4 수동 백업

**방법 1**: 스크립트 실행
```
scripts\backup-db.bat 더블클릭
```

**방법 2**: 관리 페이지에서 (권장)
1. http://localhost:5173/admin 접속
2. "백업 생성" 버튼 클릭
3. 운영 DB 또는 개발 DB 선택

### 5.5 백업 복원

관리 페이지에서:
1. http://localhost:5173/admin 접속
2. 백업 목록에서 원하는 백업의 "복원" 버튼 클릭
3. 복원 대상 DB 선택 (운영 또는 개발)

> ⚠️ 복원 시 대상 DB의 기존 데이터가 덮어씌워집니다!

### 6.1 스크립트 목록

| 스크립트 | 설명 |

3. 방향 선택 (운영→개발 또는 개발→운영)

## 8. 문제 해결

### 8.1 서버가 시작되지 않을 때

1. PostgreSQL 서비스 실행 확인
2. 포트 충돌 확인 (8000, 8001, 5173, 5174)
3. 가상환경 활성화 확인

### 8.2 DB 연결 실패

1. `.env.production` 또는 `.env.development`의 DB 설정 확인
2. PostgreSQL 서비스 상태 확인
3. DB 존재 여부 확인

### 8.3 백업 실패

1. PostgreSQL bin 경로 확인 (`scripts/backup-db.bat`)
2. DB 비밀번호 확인
3. 백업 폴더 권한 확인

### 8.4 "컬럼이 없음" 에러

DB 스키마와 코드가 불일치할 때 발생합니다.

**해결 방법**:
```bash
cd backend
set APP_ENV=production   # 또는 development
alembic upgrade head
```

그 후 서버 재시작

### 8.5 SQLAlchemy Relationship 에러

```
Could not determine join condition between parent/child tables
```

모델에서 같은 테이블을 참조하는 foreign key가 여러 개일 때 발생합니다.

**해결 방법**: relationship에 `foreign_keys` 명시
```python
supplier = relationship("Supplier", foreign_keys=[supplier_id])
```

### 8.6 Pydantic ValidationError (Extra inputs not permitted)

`.env` 파일에 새 환경변수가 있는데 `Settings` 클래스에 해당 필드가 없을 때 발생합니다.

**해결 방법**: `backend/app/core/config.py`의 `Settings` 클래스에 필드 추가
```python
SERVER_PORT: int = 8000
```

## 10. 참고 사항

- 운영 서버는 안정성을 위해 자동 리로드가 꺼져 있습니다.
- 개발 서버는 코드 변경 시 자동으로 재시작됩니다.
- 두 환경은 완전히 분리되어 있어, 개발 중 운영 데이터에 영향을 주지 않습니다.
- 마이그레이션 적용 후에도 서버가 캐시된 DB 연결을 사용할 수 있으므로, 스키마 변경 후에는 서버를 재시작하세요.
